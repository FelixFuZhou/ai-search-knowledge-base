# 主线项目：带审批的订单取消 / 退款 Agent

> **它的唯一目的是产出 L2 素材**——「我踩过哪个，具体数字是多少」。
>
> 不是为了做出一个好产品。**每个里程碑都要求你先制造问题、观察它、再修复**，因为面试问的是问题不是功能。

## 为什么选这个题

- 直接对上两道真题形态：Sierra 的客服 Agent（[D3](../系统设计/真题清单.md)）、Scale AI 的理赔 Agent（[D2](../系统设计/真题清单.md)）
- 覆盖了 Agent 岗的全部核心难点：工具契约、幂等、HITL 审批、状态恢复、权限、评测、注入防护
- 60 题里约 40 题能从它取素材

## 技术选型（建议，不强制）

选型不是重点，**别在这上面花时间**。建议最小依赖：

- 模型：Claude（`claude-sonnet-5`）或任意支持 tool use 的模型
- 编排：**先手写循环**，不要一上来用框架。手写过一遍你才说得清框架替你解决了什么（这本身是面试加分项）
- 状态：SQLite 就够
- Trace：结构化 JSON 日志起步，M4 之后可接 Langfuse / Phoenix
- 工具后端：Mock 一个订单服务（FastAPI），**必须能人为注入超时和 500**

## 里程碑

每个里程碑三段：**做什么 → 制造什么问题 → 产出哪些题的 L2**。

### M0 · 只读 loop + trace

**做什么** —— 代码骨架已写好，见 [code/](code/README.md)

- 一个 `get_order` 只读工具，3 步上限的 tool-use loop
- 从第一行代码就有 **trace**：每步的输入、工具入出参、耗时、token、终止原因
- 手写循环而非 SDK 的 `tool_runner`（理由见 [code/README.md](code/README.md)）

**制造问题** —— 三步演练，别跳过

```bash
python run.py 4 --no-trace   # 只看输出，试着回答「为什么失败」，计时
python run.py 4              # 看 trace，同一个问题，这次多久
```

case 4 查的是别人的订单。关掉 trace 时你只会看到「没查到」，
分不清是订单不存在、模型没调工具、参数错了、还是权限被拒。

**产出 L2**：[Q19](../题库/C-Agent边界与工具可靠性.md#q19) [Q21](../题库/C-Agent边界与工具可靠性.md#q21) [Q50](../题库/F-评测可观测与排错.md#q50)

> 记录：没有 trace 时定位一个问题花了 ___ 分钟；有 trace 后花了 ___ 分钟。**这个数字对比在面试里很有说服力。**

### M1 · 工具契约 + 澄清

**做什么**
- 加 `get_order_history`、`check_refund_eligibility`
- 每个工具：完整 schema、枚举优先、结构化错误返回
- 参数不全时**先澄清再调用**

**制造问题**
1. 故意把 `get_order` 和 `get_order_history` 的描述写得相似 → 统计**混用率**
2. 故意让 `reason` 是自由字符串 → 观察模型编出多少种理由
3. 造一个「用户有多个相似订单」的场景 → 看模型会不会自己挑一个

**产出 L2**：[Q23](../题库/C-Agent边界与工具可靠性.md#q23) [Q24](../题库/C-Agent边界与工具可靠性.md#q24) [Q25](../题库/C-Agent边界与工具可靠性.md#q25)

> 记录：描述优化前混用率 ___%，优化后 ___%。

### M2 · 审批网关 + 权限

**做什么**
- 加 `submit_refund`（不可逆）
- 审批网关：金额 > 阈值必须人工审批，**展示真实参数不是模型措辞**
- 审批状态**持久化**
- 权限三层：工具级 allowlist、参数级校验、**资源级 ACL**（订单必须属于当前用户）

**制造问题**
1. 先把「金额 > 500 需审批」**写在 system prompt 里**，然后用注入测试绕过它 → 体验为什么必须在网关
2. 先让审批状态**存内存**，重启服务，观察待审批任务全丢
3. 先只做工具级鉴权，然后用别人的 order_id 查询 → 观察越权成功

**产出 L2**：[Q44](../题库/E-编排多Agent与协议.md#q44) [Q54](../题库/G-安全与上线.md#q54) [Q21](../题库/C-Agent边界与工具可靠性.md#q21)

### M3 · 幂等 + 错误处理 + 循环控制

**做什么**
- `submit_refund` 加幂等键（**任务创建时生成一次**，重试复用）
- 错误分类：可重试 / 不可重试；指数退避 + 抖动
- 循环控制：step / token / 时长多维预算 + 重复调用检测

**制造问题**
1. **先用 `order_id + timestamp` 做幂等键**，然后注入超时触发重试 → 观察产生两笔退款
2. 让工具连续失败，观察 max_steps 被重试耗尽，用户等了很久拿到「失败」
3. 观察模型「换个说法再试一次」如何绕过参数精确匹配的循环检测

**产出 L2**：[Q26](../题库/C-Agent边界与工具可靠性.md#q26) [Q27](../题库/C-Agent边界与工具可靠性.md#q27) [Q22](../题库/C-Agent边界与工具可靠性.md#q22)

> 记录：重复退款复现的具体条件；修复后连发两次请求的断言测试。

### M4 · 评测体系

**做什么**
- golden set **30–50 条，分七层**（正常/边界/缺参/相似候选/工具失败/应拒绝/应转人工）
- 评分分三层：最终结果 / 工具选择与参数 / 完整轨迹
- 确定性评分做门禁，LLM judge 只评语义

**制造问题**
1. **先做一版全是 happy path 的 30 条** → 记录虚高的通过率
2. 补齐分层后 → 记录真实通过率
3. **加轨迹断言前后对比** → 记录掉了多少个百分点（这些就是「文本正确但没干活」的）
4. 写一条 **output pass / trajectory fail** 的 case

**产出 L2**：[Q45](../题库/F-评测可观测与排错.md#q45) [Q46](../题库/F-评测可观测与排错.md#q46) [Q47](../题库/F-评测可观测与排错.md#q47) [Q28](../题库/C-Agent边界与工具可靠性.md#q28)

> 记录：全 happy path 通过率 ___% → 分层后 ___% → 加轨迹断言后 ___%。**这组数字是整个项目最值钱的素材。**

---

### M5 · 长任务恢复 + 上下文控制

**做什么**
- 20 步模拟任务，上下文压缩：结构化状态 + 历史摘要 + 原文可检索
- checkpoint，**恢复时查后端真实状态而非重放**
- 部分成功作为独立状态

**制造问题**
1. **先不做压缩**跑 20 步 → 记录第 15 步的 input token 是第 1 步的多少倍
2. **先用直接截断**压缩 → 观察「用户已确认」这类关键事实被截掉，模型重复提问
3. 在第 3 步注入失败后**从头重放** → 观察前两步副作用重复

**产出 L2**：[Q36](../题库/D-上下文RAG与记忆.md#q36) [Q58](../题库/G-安全与上线.md#q58) [Q30](../题库/D-上下文RAG与记忆.md#q30)

> 记录：无压缩时第 15 步 input 膨胀 ___ 倍；压缩后上界 ___ token。
