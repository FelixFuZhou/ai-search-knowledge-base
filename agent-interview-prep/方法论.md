# 方法论

## 为什么不用「一题四答卡」

面试的真实形态是**追问链**，不是问答对。面试官问一道题，听完你 30 秒的回答后，会顺着你答案里最薄弱的地方往下钻。所以准备的单元必须是「题 + 三层追问」，而不是「题 + 一个完整答案」。

同时，48 道题每题都写代码验证是做不完的（≈48 个小实验）。真正的杠杆是**一个有深度的主线项目**：它能同时喂饱 40 道题的 L2/L3，而且这才是面试官想听的——「我干过」比「我知道」高三档。

## 支柱一：一题三层追问

每道题按面试官的追问顺序准备四段，各有时间上限：

| 层 | 时长 | 面试官在问什么 | 你要给什么 |
| --- | --- | --- | --- |
| **L0** | 30 秒 | 「什么是 X？」 | 是什么 + 边界在哪。**不要念定义，先给边界** |
| **L1** | 2 分钟 | 「你为什么不用 Y？」 | 为什么这么选 + 放弃了什么 |
| **L2** | 3 分钟 | 「线上出过什么问题？」 | 会怎么坏 + **我踩过哪个，具体数字** |
| **L3** | 2 分钟 | 「你怎么知道它是对的？」 | 怎么验证 + 线上怎么发现 |

**L2 是分水岭。** 90% 的候选人只有 L0 和 L1——那是读文档就能有的。L2 只能从主线项目和故障注入来。

### 一个完整示例（Q38 为什么多 Agent 常常更差）

> **L0**（28 秒）
> 多 Agent 的成本是上下文复制和协调开销，收益是并行和专长隔离。当子任务不真正独立时，收益为负——这是它常常更差的原因，不是实现问题。
>
> **L1**（1 分 50 秒）
> 我的默认是单 Agent + 确定性状态机。只有满足三个条件我才拆：子任务输入输出契约清晰、能真并行、失败能独立回滚。代价是我放弃了编排灵活性，换来可观测性和成本可预测。反过来说，如果需求是开放式探索、子任务数量运行时才知道，那单 Agent 会写成一坨 if-else，那时候拆是对的。
>
> **L2**（2 分 40 秒）
> 我拆过 research / writer / reviewer 三个子 Agent。结果 p95 从 8s 涨到 23s，成本 3.1 倍，质量指标没变。根因是 writer 需要 research 的全部上下文，等于把同样的 token 传了两遍，而 reviewer 又传了第三遍。当时我先怀疑是 prompt 问题，改了两版没用；后来看 trace 里的 token 分布才定位到是上下文复制。合并回单 Agent 后 p95 回到 9s、成本回到 1.2 倍。
> 另外两个坑：一是子 Agent 没有 owner，research 和 writer 都去查了同一个知识库；二是没有全局预算，一个子 Agent 卡住会拖死整条链。
>
> **L3**（1 分 40 秒）
> 判据我用三个：task success rate、cost per successful task、p95 延迟。不看单条回答质量，因为单条会蒙对。做法是同一批 30 条 golden set 跑 A/B，golden set 里要有 5 条是「必须多步推理」的，否则单 Agent 会因为题太简单而虚高。线上我按任务类型分段看，因为平均值会把「简单任务变快、复杂任务变慢」抹平。

对比一下，一个只有 L0/L1 的候选人说的是：「多 Agent 会有上下文复制和协调开销，所以要谨慎使用。」——正确，但零信息量。

## 支柱二：三种表达长度，练「说」不练「写」

你的目标是**有限时间内表达出来**。写卡片不产生这个能力。

- 每题必须**出声、计时**说一遍。L0 超 40 秒 = 没提炼干净，回去砍。
- **录音，只回听第一句话**：
  - 第一句是定义（「Agent 是一种能够…」）→ **不及格**
  - 第一句是取舍或场景（「它的成本是 X，收益是 Y，所以…」/「我在退款项目里遇到过…」）→ **及格**
- 系统设计题另配 10 分钟骨架，见 [系统设计/骨架.md](系统设计/骨架.md)。

## 支柱三：主线项目是所有 L2 的唯一来源

见 [主线项目/README.md](主线项目/README.md)。规则：

- 每完成一个里程碑，回到题库总表，把该里程碑覆盖的题的 L2/L3 状态从 `空` 改成 `有素材`。
- **没有主线项目素材的题，L2 一律标 `弱`。** 面试前优先补这些，或者在回答时诚实降级为「这个我没实际踩过，但我预期的失败模式是…」——诚实降级比编造被追问穿帮好得多。

## 支柱四：故障注入，不要等 bug 找上门

见 [故障注入/清单.md](故障注入/清单.md)。6 类故障各练一次，每次**先写假设再看 trace**，记录「假设 vs 真因」。

面试高频问「讲一个你 debug 的例子」——练完你有 6 个，而且每个都有完整的假设→排查→根因→修复→回归链条。

## 支柱五：breadth-first，取消顺序门禁

「本模块不过关不进下一模块」在准备面试时是**错的**——面试不等你，而且你不知道对方先问哪块。

- **第 1 周**：60 题全部过一遍 **L0**，只求 30 秒能开口，不求深。
- **第 2–6 周**：按「被问到概率 × 当前薄弱度」排序，逐题补 L1 → L2 → L3。
- 每周固定推进主线项目，它自然会把相关题的 L2 补上。

## 日常节奏（60–90 分钟）

| 时长 | 做什么 | 产出 |
| --- | --- | --- |
| 30 分钟 | 推进主线项目 | 代码 / trace / 一条新的 L2 素材 |
| 20 分钟 | 出声过 **6 道旧题**（间隔重复，见下） | 状态表更新 |
| 20 分钟 | 新题 L0/L1 | 答题卡 |
| 10 分钟 | 录音回听第一句 + 记日志 | 日志一行 |

**间隔重复的选题规则**（每天 6 道）：
- 2 道昨天做的
- 2 道 3–7 天前做的
- 2 道状态为 `未掌握` 或 `弱` 的

## 每周固定动作

- **周中**：注入 1 类故障，写「假设 vs 真因」。
- **周末**：用骨架**现场讲一道没准备过的真题**，全程录音、计时 10 分钟。这是唯一能检验骨架是否真的内化的方式。
- **周末**：填 [评分标准.md](评分标准.md) 的周度自评表。
