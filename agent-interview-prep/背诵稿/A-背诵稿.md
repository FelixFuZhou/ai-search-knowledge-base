## Q01 · token 与 tokenizer：为什么 token 数不等于字数？

**⏱ 30 秒｜逐字背**

> Tokenizer 把文本切成子词单元，token 是模型的最小输入单位。英文一个常见词差不多就是一个 token，中文一个字通常是一到两个，代码和 JSON 因为符号密集，token 数会明显更多。所以 token 和字数不能互相换算。这在工程上影响三件事：成本估算不能按字数估、上下文截断要按 token 位置切、还有 JSON 的字段名越短越省钱。

**🦴 骨架**：① 是什么切出来的 → ② 中英文/代码的密度差异 → ③ 三个工程影响

**⏱ +60 秒｜被追问时补**

> 另外不同模型的 tokenizer 不一样，同一段文本的 token 数不能跨模型直接套用，所以做成本对比时要各自实测。
>
> 还有一个反直觉的点：把中文提示词换成英文有时候能省 token，但会损失表达精度，这是个真实的取舍，不是无脑优化。

**⚠️ 别说**：说不出中文和英文的密度差异。这题的采分点就在这里。

## Q02 · embedding 是什么？相似度为什么用余弦？

**⏱ 30 秒｜逐字背**

> Embedding 是把文本映射成定长向量，让语义相近的文本在向量空间里离得近。用余弦相似度是因为它只看方向不看模长——文本长短不应该影响相似判断。归一化之后余弦和内积是等价的，所以很多向量库直接用内积。

**🦴 骨架**：① 映射成向量 → ② 余弦只看方向 → ③ 归一化后等价于内积

**⏱ +90 秒｜被追问时补（这段是加分项）**

> 但有个坑要注意：embedding 捕捉的是分布式的共现相似，**不等于逻辑相关**。最经典的反例是「订单已取消」和「订单未取消」，这两句的余弦相似度非常高。这直接导致 RAG 会召回意思完全相反的文档。
>
> 所以生产里 embedding 只做粗召回，后面必须接一个 rerank，用 cross-encoder 做精排。
>
> 另外领域词汇——内部产品名、缩写这些——在通用 embedding 里几乎没有区分度。这时候要么微调 embedding，要么用关键词检索和向量检索做混合。

**⚠️ 别说**：只说「把文本变成向量」就停。说不出失效场景等于没答。

## Q03 · context window 的本质限制是什么？ ⭐高频

**⏱ 30 秒｜逐字背**

> 它是模型单次请求能处理的 token 总数，**输入和输出加在一起**——200K 的窗口，输入占了 190K，能生成的就只剩 10K。这个上限来自模型训练时的最大序列长度。但更关键的一点是：**它是每次调用的处理上限，不是记忆**——模型不记得上一轮，每次都得把内容重新塞进去。

**🦴 骨架**：① 单次请求的 token 总预算 → ② **输入+输出共享** → ③ **不是记忆**（这是采分句）

**⏱ +90 秒｜被追问时补**

> 补两个层次上的区分：窗口有多大是**模型属性**，由训练时的位置编码决定；实际能不能跑满是**部署约束**，瓶颈在显存里的 KV cache。这两个别混着说。
>
> 还有个现象叫 lost in the middle：就算塞得下，模型对中间位置内容的利用率明显低于开头和结尾。所以关键指令要放最前面或最后面。
>
> 常有人问「现在上下文这么大了是不是不需要 RAG 了」，我的回答是不能替代，有三个原因：**成本随长度线性涨、注意力被稀释、而且没法做权限过滤**。第三点最关键——RAG 能在检索层按用户权限过滤，全塞进去做不到。
>
> 长上下文真正适合的是单份长文档的整体理解，或者需要全局一致性的改写。不适合多文档检索和需要权限隔离的场景。

**⚠️ 别说**：「现在 context 够大了不需要 RAG」。

## Q04 · temperature / top-p / top-k 分别控制什么？

**⏱ 30 秒｜逐字背**

> Temperature 缩放 logits，改变整个概率分布的陡峭程度，趋近 0 就接近贪心解码。top-k 是只从概率最高的 k 个候选里采样，数量固定。top-p 是从累计概率达到 p 的最小候选集里采样，**数量是动态的**——分布陡的时候候选少，平的时候候选多。

**🦴 骨架**：① temperature 改分布形状 → ② top-k 固定数量 → ③ top-p 动态数量

**⏱ +90 秒｜被追问时补**

> 生产里我的默认是：**需要确定性和结构化输出的场景一律 temperature 设 0**，工具调用、分类、抽取、JSON 输出都是。
>
> 但有一点要澄清：**temperature 等于 0 不代表完全确定性**。浮点运算的非结合性、batch 组成的变化、MoE 的路由，都会带来抖动。所以「设了 0 就能做严格回归测试」是错的，评测要么容忍抖动，要么跑多次取一致性。
>
> 还有 top-p 和 temperature 同时调容易互相干扰，通常只调一个。创意场景调高的代价是幻觉率上升，这个要用评测量化，不能凭感觉。

**⚠️ 别说**：认为 temperature=0 输出完全可复现。

## Q05 · 从训练目标解释幻觉的成因 ⭐高频

**⏱ 30 秒｜逐字背**

> 幻觉的根在训练目标。预训练优化的是下一个 token 的似然，也就是「什么样的文本看起来合理」，而不是「什么是事实」。所以在知识边界之外，模型会生成分布上最像正确答案的文本——流畅、格式对、但内容是编的。对齐阶段又奖励「有帮助的回答」，隐性惩罚了「我不知道」，**把自信编造这个倾向进一步放大了**。

**🦴 骨架**：① 目标是似然不是事实 → ② 边界外生成「最像对的」 → ③ 对齐放大了自信

**⏱ +90 秒｜被追问时补（三条推论，很加分）**

> 从这个机制能推出三件事。
>
> 第一，**幻觉不可能靠在 prompt 里写「不要编造」根本解决**。只能靠外部证据、要求引用、以及无依据就拒答的策略层。
>
> 第二，**流畅度和自信度不是正确性的信号**。这一点在高风险场景特别危险，因为最可信的表象往往对应最难发现的错误。
>
> 第三，模型不知道自己不知道。对齐之后校准通常是变差的，所以不能直接信任模型自报的置信度，要用外部信号——比如证据覆盖率、检索分数、多次采样的一致性。

**⚠️ 别说**：「因为训练数据里有错误信息」。这是次要原因，不是机制。

## Q06 · 量化牺牲什么换什么？什么场景不能量化？

**⏱ 30 秒｜逐字背**

> 量化是把权重，有时候还包括激活和 KV cache，从 FP16 降到 INT8、INT4 或 FP8，用数值精度换显存和带宽。收益有两块：显存占用降低，能塞更大的模型或者更大的 batch；还有**内存带宽压力降低**——decode 阶段是访存受限的，所以量化对 decode 提速很明显。代价是精度损失，而且不同任务的敏感度差别很大。

**🦴 骨架**：① 精度换显存和带宽 → ② **decode 是访存受限所以提速明显** → ③ 敏感度因任务而异

**⏱ +90 秒｜被追问时补**

> 敏感度大致的排序是：长链推理、代码生成、数学最敏感，分类、抽取、改写比较耐受。所以在 Agent 里，**规划环节不适合激进量化，工具参数抽取可以**。
>
> KV cache 量化和权重量化是两件不同的事，前者对长上下文场景收益更大。
>
> 不该量化的场景是：已经贴着质量红线的高风险任务，还有需要严格复现的评测基线。
>
> 最关键的一条做法是——**量化之后必须用自己的 golden set 重跑**，不能直接信论文里的通用 benchmark 数字，那些和你的业务分布不一样。

**⚠️ 别说**：只说「省显存」，不提对 decode 速度的影响。

## Q07 · 微调 / RAG / 改 prompt，决策依据是什么？ ⭐高频

**⏱ 30 秒｜逐字背**

> 判据是问题的性质。缺**知识**就上 RAG，因为知识会变、要做权限隔离、还要能引用来源。缺**行为、格式或者风格**就微调，前提是有稳定的输入输出模式和足够样本。缺的只是**指令清晰度**，那就改 prompt 和上下文工程。顺序上我是 prompt、RAG、微调这么往下走，因为迭代成本和可回滚性是依次变差的。

**🦴 骨架**：① 三种缺口对应三种手段 → ② 顺序：prompt → RAG → 微调 → ③ 理由是迭代成本

**⏱ +90 秒｜被追问时补**

> 有个常见误区是拿微调注入知识。**微调不适合注入易变知识**，因为模型没法「忘记」，更新要重训，而且完全没法做权限过滤——不同用户该看到不同数据这件事微调做不到。
>
> 微调的真实成本也不在训练，在**数据构造和评测基线**。没有 golden set 你根本没法判断微调之后是变好了还是变差了。
>
> 实际上混合是常态：微调让模型学会「怎么用检索结果」和「什么时候该拒答」，RAG 提供事实。
>
> 反过来说，如果延迟和成本卡得很死，用微调的小模型去替代大模型加长 prompt，这是划算的。

**⚠️ 别说**：「微调效果更好所以优先微调」。

## Q08 · SFT / RLHF / DPO 各解决什么问题？

**⏱ 30 秒｜逐字背**

> 这三个是递进解决同一个问题：怎么让模型对齐人的偏好，同时降低数据和训练成本。SFT 是用「输入到理想输出」的示范数据做监督微调，瓶颈是很多任务人写不出那个最好的答案。RLHF 让人只需要比较两个输出哪个更好，训一个奖励模型再做 RL，解决了示范数据难造。DPO 跳过了显式的奖励模型，直接用偏好对做优化，更简单更稳定，效果接近。

**🦴 骨架**：① 递进解决同一问题 → ② SFT 瓶颈是数据难造 → ③ RLHF 用比较 → ④ DPO 绕开 RL

**⏱ +60 秒｜被追问时补**

> 有个代价叫 alignment tax：对齐之后泛化能力和校准度可能下降，模型更倾向于给出「听起来好」的答案。这个和 Q05 讲的幻觉机制是同一条线。
>
> 对 Agent 岗的意义在于——你不太会去训模型，但你要知道**为什么模型倾向于自信、倾向于说「我已经完成了」**。这是对齐目标的副产物，所以工程上必须以工具事件为真相，不能信模型的自述。

**⚠️ 别说**：把 DPO 说成「另一种 RL」。它恰恰是绕开了 RL。

## Q09 · KV cache 是什么？为什么它决定推理成本结构？ ⭐高频

**⏱ 30 秒｜逐字背**

> 自回归生成的时候，每生成一个 token 都要对前面所有 token 做注意力。KV cache 把已经算过的 key 和 value 存下来，避免重复计算，让 decode 每一步的计算量从随长度增长降到常数级。代价是显存——cache 大小正比于 batch 乘以序列长度乘以层数，长上下文加大 batch 会直接打爆显存。

**🦴 骨架**：① 缓存已算的 KV → ② 计算量降为常数 → ③ 代价是显存

**⏱ +2 分钟｜被追问时补（这段答好会被追到模块 B）**

> 它解释了推理的两阶段成本结构。**prefill 是一次性处理输入，算力受限，可以高度并行；decode 是逐 token 生成，访存受限**，瓶颈在于把 KV cache 和权重从显存搬到计算单元。
>
> 所以「输入 token 便宜、输出 token 贵」不是定价策略，是物理事实。
>
> 工程上还有个重要推论：**KV cache 才是 batch size 的真正上限，不是算力**。vLLM 的 PagedAttention 解决的就是 cache 的显存碎片问题。
>
> 对 Agent 来说，多轮循环会不断增长 cache，这是长任务成本爆炸的直接原因。

**⚠️ 别说**：说不出 prefill 和 decode 的瓶颈不同。

## Q10 · structured output 底层怎么实现的？

**⏱ 30 秒｜逐字背**

> 有两个层次。一种是 prompt 约束，就是在提示里描述格式，模型可能不遵守，需要重试和解析容错。另一种是 constrained decoding，在采样的时候直接屏蔽掉会违反 schema 的 token，**从机制上保证输出可解析**。function calling 和 tool use 一般走的是第二种，所以结构上是可靠的。

**🦴 骨架**：① 两个层次 → ② prompt 是建议 → ③ constrained decoding 是机制保证

**⏱ +90 秒｜被追问时补（关键采分点）**

> 但有一条必须强调：**结构合法不等于内容正确**。constrained decoding 能保证 JSON 解析得了、枚举值在范围内，但保证不了订单号是真的、金额是对的。
>
> 所以**服务端必须重新校验**——类型、范围、权限、业务规则。绝不能因为 schema 约束过了就直接执行。
>
> 还有个副作用：强约束会轻微降低模型质量，因为被限制的路径可能是它本来想走的，schema 越复杂越明显。所以设计上应该**拆成多个小 schema，而不是一个巨型嵌套 schema**。
>
> 另外枚举值比自由字符串好，既减少解析失败，也让「不该出现的值」这类负向测试写得出来。

**⚠️ 别说**：认为用了 structured output 就不用服务端校验。
