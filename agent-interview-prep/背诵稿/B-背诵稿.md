## Q11 · 设计推理 batching 系统（Anthropic 真题）

**⏱ 开场 30 秒｜逐字背**

> 这题的核心张力是：**攒批能提高吞吐，但攒批本身增加延迟**。用户同步等待意味着延迟有硬约束。所以它本质上是一个准入控制加排队调度的问题，不是模型问题。我先确认一下延迟目标——首 token 的 SLO 大概是什么量级？

**🦴 之后必须覆盖的五块**

```
1. 触发条件   批满 100 / 等待超 T 毫秒 / 显存达阈值，三者取先到
              T 由 SLO 反推，不是拍脑袋
2. 两阶段分开 prefill 按 token 总数攒批（算力受限）
              decode 按序列数（访存受限）
3. continuous batching  短请求先返回后立刻补位
              否则整批被最长的那条拖死
4. 队列分级   不同 SLO 的流量不能混一个队列，否则长任务饿死短任务
5. 过载策略   队列有上限，超了快速返回 429，不要无限排队
```

**⏱ 失败模式（面试官一定会问）｜背四条**

> 我预期最容易出问题的有四个：
>
> 第一是**队头阻塞**，一条超长输入把整批 prefill 拖住，所有人的首 token 延迟都飙升。解法是按 token 数限批，不是按请求数。
>
> 第二是**显存 OOM**，batch 攒够了但 KV cache 放不下。所以准入判断要按预估的 cache 占用算，不能只数请求数。
>
> 第三是**尾延迟塌方**，平均延迟正常但 p99 很差，因为长请求全堆在一起了。解法是按长度分桶。
>
> 第四是**重试风暴**，超时的客户端重试会加剧过载，需要背压和幂等。

**⏱ 验证｜背三句**

> 指标要分开看：**首 token 延迟、token 间延迟、端到端 p95 和 p99、GPU 利用率、吞吐、拒绝率**。
>
> 压测必须用混合负载，长短请求按真实分布混，只用等长请求压会得出虚高的结论。
>
> 容量看饱和点——**p95 突破 SLO 时的 QPS 才是真实容量，不是 GPU 打满时的 QPS**。

**⚠️ 别说**：全程只谈 batch size，不谈延迟 SLO 和显存约束。

## Q12 · static vs continuous batching

**⏱ 30 秒｜逐字背**

> static batching 是凑齐一批一起进、一起出，批里所有请求要等最慢的那条完成。continuous batching 是以迭代为单位调度，某条序列生成完就立刻退出，空位立刻补新请求进来。对 LLM 来说后者特别重要，因为**输出长度差异巨大而且事先不可知**——一条生成 20 个 token、一条生成 2000 个，static 下前者要陪跑一百倍时间。

**🦴 骨架**：① 一起进一起出 vs 迭代级调度 → ② **输出长度不可知**（这是根本原因）

**⏱ +60 秒｜被追问时补**

> 收益的量级：真实混合负载下吞吐通常能提升数倍，GPU 利用率从百分之三四十提到百分之八十以上。
>
> 代价是调度复杂度，而且需要 PagedAttention 这类显存管理来支持动态增删序列。
>
> 这是 vLLM、TensorRT-LLM 这类框架的核心价值——不过我说框架名的时候会说清它替我解决了什么，而不是只报名字。

**⚠️ 别说**：能定义两个名词，说不出「输出长度不可知」这个根本原因。

## Q13 · prefill 与 decode 的资源特征差异

**⏱ 30 秒｜逐字背**

> prefill 是一次性处理全部输入，**算力受限**，并行度高，影响的是首 token 延迟。decode 是逐 token 生成，**访存受限**——每一步都要把整个 KV cache 和权重过一遍显存带宽——并行度低，影响的是 token 间延迟。两个阶段的瓶颈完全不同，所以调度策略也应该不同。

**🦴 骨架**：① prefill 算力受限影响 TTFT → ② decode 访存受限影响 ITL → ③ 瓶颈不同所以要分开

**⏱ +90 秒｜被追问时补**

> 混在一起调度的问题是：**一个大的 prefill 会打断正在进行的 decode**，导致已经开始输出的用户卡顿。
>
> 分离部署的做法是把两个阶段放在不同实例，各自用最优的批策略，代价是要跨节点传 KV cache，需要高速互联。
>
> 还有个折中方案叫 chunked prefill，把长的 prefill 切片，穿插在 decode 中间，用少量的首 token 延迟换 token 间延迟的平稳。
>
> 怎么选取决于产品形态：**交互式产品优先保 ITL 平稳**，因为用户对卡顿敏感；批处理场景优先保吞吐。

**⚠️ 别说**：说不清「访存受限」具体指什么。

## Q14 · TTFT 和 ITL 分别被什么决定？

**⏱ 30 秒｜逐字背**

> 首 token 延迟等于排队时间加 prefill 时间，由输入长度、队列深度和 prefill 批策略决定。token 间延迟是每一步 decode 的时间，由模型大小、显存带宽和当前 batch 大小决定。端到端延迟等于首 token 延迟加上 token 间延迟乘以输出长度。这两个要分开优化，手段完全不同。

**🦴 骨架**：① TTFT = 排队 + prefill → ② ITL = 每步 decode → ③ 端到端公式

**⏱ +90 秒｜被追问时补**

> 优化 TTFT 主要靠 prompt caching、缩短输入、限制队列深度、chunked prefill。优化 ITL 靠量化、投机解码、减小 batch、或者换更小的模型。
>
> 但**最容易被忽略、收益往往最大的是缩短输出长度**——让模型少说废话、用结构化输出替代自然语言，端到端延迟直接线性下降。
>
> 这两个指标会互相拉扯，加大 batch 提吞吐但抬高 ITL。所以必须先定 SLO 再优化，否则会在两个指标之间反复横跳。

**⏱ +60 秒｜Agent 场景特有（很加分）**

> Agent 是多轮串行调用，端到端延迟是每轮之和。一轮两秒，五轮就是十秒。
>
> 所以 **Agent 的延迟优化重点是减少轮数**，比如更好的工具设计、并行工具调用，而不是单轮提速。
>
> 流式输出能改善感知延迟，但对需要等工具结果才能说话的 Agent 用处有限，这时候要给中间状态反馈，比如「正在查询订单」。

**⚠️ 别说**：只说「优化延迟」，不区分两个指标。

## Q15 · 吞吐与延迟怎么权衡？SLO 怎么定？

**⏱ 30 秒｜逐字背**

> 这两个本质冲突——提吞吐靠攒批和高并发，两者都抬高单请求延迟。所以正确的顺序是**先定延迟 SLO 当约束，再在约束下最大化吞吐**。反过来做一定会失控，因为吞吐是可以无限追的。

**🦴 骨架**：① 本质冲突 → ② SLO 是约束不是目标 → ③ 顺序不能反

**⏱ +90 秒｜被追问时补**

> SLO 要分档定，不能一个数覆盖所有流量。交互式对话大概是首 token p95 一秒以内、token 间 p95 五十毫秒以内；Agent 的后台任务是端到端 p95 三十秒以内，首 token 不敏感；批处理没有延迟 SLO，只看吞吐和成本。
>
> 一定要用 **p95 和 p99，不是平均值**。平均会被大量快速请求拉低，掩盖尾部体验。
>
> 定 SLO 的依据应该是用户行为数据——超过多久用户会流失或者重试，而不是技术上能做到多少。
>
> 容量规划看饱和点，就是 p95 突破 SLO 时的 QPS。

**⚠️ 别说**：给一个统一 SLO 覆盖所有流量类型。

## Q16 · 设计 GPU 配额 / credit 管理系统（OpenAI 真题）

**⏱ 开场 30 秒｜逐字背**

> 我会先把三件事分开：**配额是能用多少，限流是多快能用，计费是用了多少**。很多设计把三者混为一谈，后面就理不清了。另外计量单位不能用请求数——LLM 请求的成本差异极大——要用 token，而且输入输出分别计价，因为它们的成本结构本来就不同。

**🦴 之后必须覆盖的五块**

```
1. 预扣 + 结算   请求前按 max_tokens 预扣，完成后按实际用量结算并退还
                 否则挡不住「一个请求打爆配额」
2. 双维度限流   RPM 和 TPM 都要限，只限一个都会被绕过；用 token bucket
3. 分布式一致性 Redis 原子操作，或本地限流 + 全局异步校正
                （容忍少量超发换低延迟）
4. 多租户公平   每租户独立桶 + 全局桶双层，防止单租户饿死其他人
5. 超限行为     返回 429 + Retry-After，让客户端能正确退避
                直接丢弃会引发重试风暴
```

**⏱ 失败模式｜背三条**

> 我预期三个坑。一是**流式请求的计费时点**——连接中断时已经生成的 token 要不要计费，不处理会被刷。二是**预扣过度**，用户都填最大值但实际只用一小部分，配额被虚占，需要按历史实际用量做动态预扣。三是**时钟漂移**导致多副本的限流窗口不对齐，出现瞬时超发。

**⏱ 验证｜背两句**

> 并发压测断言总用量不超配额，单租户超限不影响其他租户，限流本身增加的延迟控制在五毫秒以内。
>
> 另外计费数据要和实际推理日志按天对账，偏差超过千分之一就告警。

**⚠️ 别说**：用请求数做配额单位。

## Q17 · prompt caching 怎么生效？prompt 怎么配合它？ ⭐必背

**⏱ 30 秒｜逐字背**

> 缓存的是 prefill 阶段算出来的 KV cache，命中之后跳过这部分重算，直接降低首 token 延迟和输入成本。但命中条件很严格——**前缀必须完全匹配**，从第一个 token 开始逐 token 一致，一旦某个地方不同，后面全部失效。而且匹配通常是按块做的，还有最小可缓存长度，太短的 prompt 根本不进缓存。

**🦴 骨架**：① 缓存的是 prefill 的 KV → ② **前缀完全匹配**（这是关键约束）

**⏱ +2 分钟｜被追问时补（这段是采分重点）**

> 所以设计 prompt 的时候要**按变化频率从低到高排列**：系统指令和工具定义放最前面，然后是长期知识和 few-shot，再是会话历史，最后才是本轮输入。前半段稳定的部分就能一直吃到缓存。
>
> 最常见的错误是把**时间戳、随机 ID、用户名放在 prompt 开头**，这样缓存永远不命中。
>
> 还有一点：工具定义要放前面而不是穿插在中间；工具集频繁变动会击穿缓存，这是「工具集要稳定」的一个额外理由。
>
> 需要注意缓存有 TTL，低频调用命中率低；缓存写入本身可能有额外成本，所以要算净收益，不是无脑开。
>
> **Agent 场景收益最大**，因为多轮循环里系统指令和工具定义每轮都重复，缓存能省掉大部分输入成本。

**⏱ +60 秒｜排错（加分）**

> 命中率上不去的时候我的排查顺序是：先看前缀里有没有变量，再看工具定义是不是被动态排序了——**字典序列化顺序不稳定是个经典坑**——然后看是不是超过 TTL，最后看有没有达到最小可缓存长度。
>
> 缓存命中率是个必须上 dashboard 的指标，否则成本悄悄涨了都不知道。

**⚠️ 别说**：说不出「前缀完全匹配」这个约束，或者说不出该把什么放前面。

## Q18 · Agent 请求的成本构成？怎么定位大头？ ⭐必背

**⏱ 30 秒｜逐字背**

> 成本等于每一轮的输入 token 加输出 token，再加上工具调用、检索和重试的成本。但关键认知是——**Agent 的成本随轮数近似平方增长**，因为每一轮都要把之前的全部历史再传一遍当输入。所以「减少轮数」通常比「换便宜模型」收益更大。

**🦴 骨架**：① 成本构成 → ② **轮数的平方效应**（这是采分句） → ③ 所以优先减轮数

**⏱ +2 分钟｜被追问时补**

> 定位大头我按三步走。
>
> 第一看**轮数分布**，p50 和 p95 的轮数，长尾任务往往贡献了大部分成本。
>
> 第二看**单轮输入的构成**——系统指令、工具定义、历史、检索结果，哪一块最胖。检索结果是最容易被忽略的大头，top-k 从 5 改到 20，成本涨四倍但质量常常不变。
>
> 第三看**重试和失败**。失败任务的成本是纯损失，所以「失败任务的成本占比」是个高信号指标。
>
> 正确的成本指标是 **cost per successful task，不是 cost per call**。后者会奖励「早早失败」这种坏行为。
>
> 优化手段按性价比排是：prompt caching、压缩历史、缩小工具集、模型分级路由、并行工具调用，最后才是换模型。
>
> 这里会被追问一句「开了 prompt caching 之后还是平方吗」。**还是平方，但系数被打下来了**——重复的前缀走缓存读，价格大概是原价的十分之一量级。所以缓存不改变增长的形状，改变的是斜率；轮数真的多起来，压缩历史仍然躲不掉。

**⏱ +60 秒｜失败模式（推演版，可背）**

> 成本失控最常见的三个原因是：**循环没有预算上限、检索结果全量塞进上下文、失败之后无限重试**。
>
> Trace 里必须记每一轮的输入输出 token、缓存命中、工具耗时、总轮数和终止原因，否则事后完全没法归因。
>
> Dashboard 要按任务类型分段看成本，平均值会把大量廉价的简单任务和少量昂贵的复杂任务混在一起。

**⚠️ 别说**：只说「token 贵」，说不出轮数的平方效应。
