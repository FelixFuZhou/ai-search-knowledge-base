## Q19 · 什么是 Agent？与单次调用、与 workflow 的边界？ ⭐必背

**⏱ 30 秒｜逐字背**

> 我会用**控制流由谁决定**来区分这三个。单次调用没有控制流；workflow 的控制流写死在代码里，模型只负责填空；**Agent 的控制流是模型在运行时决定的**——下一步做什么、还要不要继续，是模型的输出。所以 Agent 的定义性特征是「模型进入了控制流」，不是「有工具」，也不是「多轮」。

**🦴 骨架**：① 区分点是控制流归属 → ② 三者各自的控制流在哪 → ③ **不是「有工具」也不是「多轮」**

**⏱ +90 秒｜被追问时补**

> 由这个定义能直接推出取舍：**模型进入控制流，换来的是适应性，付出的是可预测性**。所以步骤事先能枚举就用 workflow，枚举不了才用 Agent。
>
> 按这个标准，多轮聊天不是 Agent，因为没有环境反馈和目标状态；固定的「检索再生成」也不是，因为控制流是写死的。
>
> 实际项目里混合往往最优：**外层用确定性状态机，内层某几个节点用单步 Agent 做受约束的选择**。我自己的项目就是这个架构。

**⏱ +60 秒｜「怎么判断该不该用」（加分）**

> 有个很实用的判断方法：先用 workflow 实现，然后统计**兜底分支的触发率**。触发率低说明 workflow 就够了，不需要 Agent。

**⚠️ 别说**：第一句说「Agent 是一种能自主完成任务的智能体」。

## Q20 · 哪些需求不该用 Agent？ ⭐必背

**⏱ 30 秒｜逐字背**

> 四类不该用。一是**步骤固定且可枚举**，代码更快更便宜更可测。二是**容错率极低**，比如支付、医疗、法律出具，不可预测性的代价太高。三是**延迟和成本敏感**，因为 Agent 的多轮循环成本随轮数快速增长。四是**需要严格可复现**，比如审计和合规场景，模型输出天然有抖动。

**🦴 骨架**：四类 —— 可枚举 / 低容错 / 高成本敏感 / 要可复现

**⏱ +90 秒｜被追问时补**

> 我的判断句式是一句话：**「这个需求的分支能不能事先枚举完？」**能就不用 Agent。
>
> 但真实场景往往是**部分该用**——意图识别和参数澄清用模型，因为用户表达是开放的；执行流程用代码，因为步骤是固定的。把「用不用 Agent」当成二选一是新手的标志。
>
> 反过来说，Agent 真正不可替代的场景只有一个特征：**下一步依赖上一步的结果，而且这个依赖关系事先不知道**。
>
> 我的默认立场是先用确定性方案试，试不动了再上 Agent。

**⚠️ 别说**：答不出「先用确定性方案」这个默认立场。

## Q21 · 生产 Agent 的最小组件有哪些？

**⏱ 30 秒｜逐字背**

> 我一般分八层：**model 是选型和版本固定；instructions 是版本化的系统指令；state 分会话状态和任务状态；tools 包括 schema、实现和权限；policy 是预算、审批和允许禁止的动作；runtime 管循环控制、超时、重试；observability 是 trace 和指标；eval 是 golden set 加回归门禁。**

**🦴 骨架**：model / instructions / state / tools / **policy** / runtime / observability / eval

**⏱ +90 秒｜被追问时补（采分重点）**

> 重点是：**Demo 和生产的差别不在前四层，在后四层**。Demo 缺的是 policy、observability 和 eval。
>
> 最容易被漏掉的是 **policy 层**。很多人把预算和权限写进 prompt，但 **prompt 是建议，policy 必须在执行层强制**。
>
> 还有 **state 必须区分两种**：会话状态可以丢，重建就行；任务状态不能丢，因为它涉及副作用。混在一起会导致重启之后重复执行。

**⏱ L2 推演版｜可背**

> 我预期这里最容易出问题的是两件事。
>
> 一是**没有 trace 的时候所有排错都是猜**——现象只能看到「失败了」，看不到在哪一步偏的。
>
> 二是**把权限写在 prompt 里**，一次注入测试就能绕过去。

**📝 素材槽**（做完主线项目 M0/M2 后替换上面这段）
> 「我在一个退款 Agent 里，一开始没写 trace，一个『取消失败』查了 ___ 分钟；补上 trace 之后同类问题 ___ 分钟定位。」

**🔻 暂时的降级话术**
> 「这个我还没在生产规模上踩过，但我在自己的项目里验证过 trace 前后的排错效率差异，这也是我现在会从第一行代码就写 trace 的原因。」

**⚠️ 别说**：只答「模型加工具加循环」。

## Q22 · 如何定义任务的成功、失败与停止？

**⏱ 30 秒｜逐字背**

> 成功必须是**可被后端验证的状态**，不能是模型的自我声明。停止条件至少四类：达成目标、超预算、不可恢复的错误、需要人介入。预算要多维度同时限——步数、token、时长、金额。失败也要分类，不能只有一个 failed，至少要分参数不足、无权限、工具失败、无资格、用户放弃。

**🦴 骨架**：① 成功=后端可验证 → ② 四类停止 → ③ 多维预算 → ④ 失败要分类

**⏱ +90 秒｜被追问时补**

> 失败为什么要分类？因为**不同失败对应不同的下一步动作**——澄清、拒绝、重试还是转人工——以及不同的告警级别。一个笼统的 failed 会让线上完全没法运营。
>
> 每个终止状态都要有**明确的用户可见结果**。静默停止是最差的失败模式，用户完全不知道发生了什么。
>
> 预算多维度这一点也有原因：**只限步数，模型会在单步里塞进巨大的上下文；只限 token，会无限循环小步骤**。

**⏱ L2 推演版｜可背**

> 我预期最容易出的问题是：**只设了最大步数，结果工具连续超时的时候，所有步数全耗在重试上**，用户等很久最后拿到一个「失败」。正确的做法是同时加总时长预算，而且让重试不计入步数但计入时长。
>
> 另一个是：模型在遇到「业务规则拒绝」的时候，会不停尝试其他工具找变通路径，因为终止条件里没有把「业务拒绝」定义成一个合法终态。

**🔻 降级话术**
> 「这个我没在生产上踩过，但我预期最容易出问题的是预算维度不全，所以我会同时限步数、token 和总时长。」

**⚠️ 别说**：只说「设置最大步数」。

## Q23 · 好的工具 schema 怎么设计？ ⭐必背

**⏱ 30 秒｜逐字背**

> 六条：**单一职责**；名称和描述要让模型能区分；**强类型，枚举优先于自由字符串**；入参尽量少；**结构化的错误返回**；还有幂等标识。另外描述是写给模型看的，重点应该是**什么时候该用、什么时候不该用**，而不是这个函数干了什么。

**🦴 骨架**：单一职责 / 描述可区分 / 枚举优先 / 少入参 / 结构化错误 / 幂等标识

**⏱ +2 分钟｜被追问时补（采分重点）**

> 为什么必须拆分而不是做一个大工具？如果设计成 `manage_order(action = cancel 或 query 或 refund)`，模型的选择空间就从工具空间变成了参数空间，**这样既没法做工具级的权限控制，也没法写「不应调用」的负向测试**。
>
> 描述里加**反例**收益特别大。比如 `get_order` 我会写「当用户询问订单状态时使用；**当用户想取消订单时不要用这个，用 cancel_order**」。
>
> 错误返回我会结构化成 code、message、retryable、user_message 四个字段。retryable 让 runtime 能自动判断，user_message 保证不会把内部信息泄露给用户。
>
> 还有一点容易忽略：工具定义会占 prompt 而且影响缓存命中，所以**工具集要稳定而且精简**。

**⏱ L2 推演版｜可背**

> 我预期最容易出问题的是**自由字符串参数**。比如取消原因如果是自由文本，模型会编出各种五花八门的理由，下游统计全乱。改成枚举之后不只是统计干净了，**模型的工具选择准确率也会上升**，因为枚举缩小了它的想象空间。

**📝 素材槽**（主线项目 M1）
> 「我把 reason 从自由字符串改成枚举后，下游统计从 ___ 种理由收敛到 ___ 种，同时工具选择准确率从 ___ 升到 ___。」

**⚠️ 别说**：设计一个 `execute_action(action, params)` 的万能工具。

## Q24 · 如何防止模型调用错误的工具？ ⭐必背

**⏱ 30 秒｜逐字背**

> 五层防御。**第一是精简工具集**，这是最有效的一招，工具数量和选择准确率是负相关的。第二是描述要有区分度，尤其相似工具，要显式写「不该用的场景」。第三是工具路由，按意图先分组，只暴露相关子集。第四是 allowlist，按角色和阶段限制，**在执行层拦截**。第五是负向测试。

**🦴 骨架**：精简 → 描述区分 → 路由分组 → allowlist → 负向测试

**⏱ +90 秒｜被追问时补（采分重点）**

> 关键在于：**前三层降低概率，后两层保证安全**。只做前三层是不够的，概率再低乘以流量还是事故。
>
> 工具数量有个经验阈值，超过十到十五个准确率会明显下降。超了就要分组，或者改成两阶段——先选组，再选工具。
>
> 还有一条：**澄清优于猜测**。模型不确定的时候应该问，而不是挑一个最像的。这个要在系统指令里显式要求，而且要在 eval 里奖励澄清行为，否则模型会被优化成不问。

**⏱ L2 推演版｜可背**

> 我预期最典型的问题是**描述雷同导致的混用**。比如 `get_order` 和 `get_order_history`，如果描述都写「查询订单信息」，模型会长期混用。改成「`get_order` 按订单号查单个订单的当前状态」和「`get_order_history` 查某用户最近的多个订单，**已知订单号时不要用**」，混用率会明显下降。

**📝 素材槽**（主线项目 M1）
> 「描述优化前混用率 ___%，优化后 ___%。」

**⏱ L3｜背两句**

> 评测上必须**把工具选择和最终回答分开测**。因为回答对了但工具选错，会被最终答案的评分掩盖掉。
>
> 每个工具至少三条测试：正确调用、参数不全时不调用、**不该调用时不调用**。第三条最常被漏。

**⚠️ 别说**：只答「把 prompt 写清楚」。

## Q25 · 用户参数不全时怎么办？ ⭐必背

**⏱ 30 秒｜逐字背**

> 原则是**调用之前把必填参数收集齐，缺了就问，不猜**。schema 里要明确区分 required 和 optional。遇到模糊值，比如「上周那个订单」，要**回显候选让用户确认**，不能自己选一个。另外澄清要一次问全，不要挤牙膏式一轮问一个。

**🦴 骨架**：① 调用前收齐 → ② required/optional 明确 → ③ **模糊值回显确认** → ④ 一次问全

**⏱ +90 秒｜被追问时补（采分重点）**

> 这里最危险的不是「没问」，而是**猜了而且大部分时候猜对了**。这会让问题在测试里完全隐形，然后在长尾里爆发。
>
> 什么时候可以不问？只有能从上下文**唯一确定**的时候。「唯一」是关键——只要有两个候选就必须问。
>
> 澄清次数也要有预算，无限澄清等于死循环。我一般设两次问不清就转人工。

**⏱ L2 推演版｜可背**

> 我预期最容易出的问题是**只有一个候选时跳过确认**。比如用户说「取消我的订单」，系统里只有一个进行中订单，模型直接就取消了——这看起来完全合理。但用户实际可能指的是另一个已完成订单想退货。
>
> 所以我的做法是：**永远先回显订单详情让用户确认，哪怕只有一个候选**。这会让澄清轮次上升，但错误取消是不可逆的，这个代价值得。

**📝 素材槽**（主线项目 M1 / 故障注入 F3）
> 「我造了三个金额和时间都接近的订单做测试，模型在 ___ 的情况下会自己挑一个，加了强制回显之后错误率归零。」

**⏱ L3｜背一句**

> eval case 必须覆盖四种：无参数、参数模糊、**有多个相似候选**、参数明确。第三种最容易出错，而且「有多个候选时是否询问」应该是一条独立的评分项。

**⚠️ 别说**：答「用默认值」。

## Q26 · 工具有副作用，如何避免重复执行？ ⭐必背

**⏱ 30 秒｜逐字背**

> 四件事：**幂等键**，按业务维度构造，比如订单号加动作加请求 ID；**执行前先查状态**；**明确的用户确认**；还有**按失败类型决定要不要重试**。而且幂等的保证点必须在**服务端**，不在 Agent，Agent 只负责传一致的幂等键。

**🦴 骨架**：幂等键 / 查状态 / 确认 / 失败分类。**保证点在服务端**

**⏱ +2 分钟｜被追问时补（采分重点）**

> 重试有个两难：**网络超时的时候你不知道对方到底执行没执行**。这个问题只有幂等能解决，任何重试策略都解决不了。
>
> 幂等键必须**在第一次调用之前生成并持久化，重试的时候复用**。如果每次重试都生成新键，那等于没有幂等——这是最常见的实现错误。
>
> 失败要分类：超时、5xx、限流是可重试的；4xx 和业务规则拒绝是不可重试的，重试只会浪费预算。
>
> 如果外部系统本身不支持幂等，就得用 Saga 或者补偿事务。

**⏱ L2 推演版｜可背**

> 我预期最容易出的问题是**幂等键构造错误**。比如用「订单号加时间戳」，时间戳每次重试都在变，等于没有幂等，超时重试就会产生两笔退款。
>
> 还有一个更隐蔽的：**Agent 循环重启之后从头开始，但之前的副作用已经发生了**。所以恢复的时候必须先查后端真实状态，而不是重放动作。

**📝 素材槽**（主线项目 M3 / 故障注入 F2）
> 「我故意用 order_id 加 timestamp 做幂等键，注入超时触发重试，复现出了两笔退款；改成任务创建时生成一次 request_id 并持久化之后，连发两次只产生一次动作。」

**⏱ L3｜背一句**

> 必须有一条测试进 CI：**同一个请求连发两次，断言只产生一次副作用**。更强的做法是在工具调用之后注入超时，验证重试之后仍然只有一次。

**⚠️ 别说**：只说「加幂等键」，说不出键怎么构造、什么时候生成。

## Q27 · 工具超时或 500 怎么处理？如何避免无限循环？

**⏱ 30 秒｜逐字背**

> 工具错误要**结构化地返回给模型**，让它能做出正确决策，而不是抛异常或者把原始堆栈丢回去。返回给模型的内容里绝对不能有堆栈、内部主机名、SQL 或者密钥。循环控制上，用步数、token、时长多维预算，加上**重复调用检测**——同一个工具同样参数连续几次就跳出——还要有明确的 abort 终态。

**🦴 骨架**：① 结构化错误 → ② 不泄露内部信息 → ③ 多维预算 + 重复调用检测 + 明确终态

**⏱ +90 秒｜被追问时补**

> 给模型看的错误信息应该是**可行动的**。「订单服务暂时不可用，可以稍后重试」比「HTTP 500」有用得多——前者模型知道该告诉用户等待，后者它可能去乱试别的工具。
>
> 退避要用指数退避加**抖动**。抖动很重要，否则多个失败请求会同步重试，形成尖峰。
>
> 部分成功要显式建模。三个工具调用成功了两个，状态不是「失败」而是「部分完成」，恢复的时候只补没做的那个。
>
> 还有**循环检测应该比预算更早生效**。模型卡在同一个失败工具上的时候，十步预算会全部耗掉，但连续三次相同调用就应该跳出了。

**⏱ L2 推演版｜可背**

> 我预期两个坑。
>
> 一是模型会「换个说法再试一次」——参数微调但语义相同，所以**参数精确匹配的循环检测会失效**。需要对参数做归一化，去掉自由文本字段之后再比较。
>
> 二是**超时的工具其实执行成功了，只是响应慢**。模型收到「失败」告诉用户失败，但用户看到的是操作已完成。所以超时之后应该去查状态，而不是假设失败。

**⏱ L3｜背一句**

> 测试要模拟超时、500、429，断言四件事：不泄露内部信息、有用户可见的说明、不无限重试、最终进入明确终态。另外人为让工具连续失败，断言 Agent 在预算内停止并给出可理解的结论。

**⚠️ 别说**：把原始异常直接塞回给模型。

## Q28 · 模型说「已完成」但没调用工具，怎么避免？ ⭐必背（试金石题）

**⏱ 30 秒｜逐字背**

> 根本原则是：**真相来源是工具事件和后端状态，不是模型说的话**。所以实现上，面向用户的成功回复必须由**已验证的工具结果**渲染出来，而不是让模型自由生成。而且这个现象不是 bug，是对齐的副产物——模型被训练成倾向于给出「有帮助的、完成态的」回答。

**🦴 骨架**：① 真相是工具事件 → ② 终态回复由代码组装 → ③ **这是对齐的副产物不是 bug**

**⏱ +2 分钟｜被追问时补（采分重点）**

> 我会做三层防护。
>
> **架构层**：终态回复由代码根据工具返回值组装，模型只负责措辞。
>
> **校验层**：模型声称成功的时候，检查本轮有没有对应的成功工具事件，没有就拦截，然后重试或者转人工。
>
> **评测层**：做轨迹评测，断言「工具 X 被调用而且成功」，而不只是断言回答里出现了「已取消」这几个字。
>
> 我想强调的是：在有副作用的场景里，**让模型完全自由生成终态回复是架构缺陷，不是 prompt 问题**。改 prompt 只能降低概率，降不到零。

**⏱ L2 推演版｜可背**

> 我预期这个问题最常出现在**工具超时之后**——模型收到超时错误，但还是回复「您的订单已成功取消」，因为它把「用户想取消」和「流程走完了」混为一谈了。
>
> 还有一个更隐蔽的变体：**工具调用成功了，但返回的是「无资格退款」，模型仍然说「退款已提交」**。它把工具调用成功当成了业务成功。所以校验要看的是**业务结果字段，不是 HTTP 状态**。

**📝 素材槽**（主线项目 M4）
> 「我加了轨迹断言之后，一批原本 ___% 通过的用例掉到 ___%，差额全是『文本正确但工具没调用或者调用失败后模型自己圆场』——这 ___% 在线上就是投诉。」

**⏱ L3｜背两句**

> 必须写一条测试：**回答文本正确但工具未调用，判为 fail**。这条 case 是检验你的评测体系有没有轨迹维度的最快方法。
>
> 线上监控看「声称成功」和「后端实际成功」的差值，这个指标为零才算真的解决。

**⚠️ 别说**：答「在 prompt 里强调必须调用工具」。
