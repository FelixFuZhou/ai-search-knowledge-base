## Q29 · context / session state / long-term memory / RAG 的边界？ ⭐必背

**⏱ 30 秒｜逐字背**

> 我按**生命周期和读写规则**来区分，不是按存储介质。**context** 是本次调用送进模型的全部内容，生命周期就是这一次调用，它是每次重新组装的产物。**session state** 是当前任务或会话的状态，会话期有效，可以丢，重建就行。**long-term memory** 是跨会话的用户偏好和事实，长期有效，**写入需要门禁，读出来要当不可信数据**。**RAG** 是外部事实知识，随源数据更新，可信度高但有时效和权限问题。

**🦴 骨架**：四者按 生命周期 / 谁写 / 可信度 三个维度分

**⏱ +90 秒｜被追问时补**

> 最容易混的是 **session state 和 long-term memory**。前者可以丢，后者不能随便写——因为一次错误写入会污染之后所有的会话，而且很难被发现。
>
> 还有一个常见错误是把 **context 当成存储**。它是每次重新组装出来的，把它当存储会导致「以为模型记住了」这种误判。
>
> 四者的错误用法我总结成三条：**把任务状态放长期记忆会污染；把事实知识写进 prompt 会没法更新也没法做权限；把长期记忆当事实用是危险的，因为它没经过验证。**

**⏱ L2 推演版｜可背**

> 我预期最危险的一类问题是**记忆被当成授权**。比如把「用户说他喜欢快速退款」写进长期记忆，后来模型把这条当成了授权，在另一个会话里跳过了确认步骤。
>
> 记忆里存的是**偏好，不能当策略用**。这是个必须在架构上隔开的边界。

**⏱ L3｜背一句**

> 每一类数据都要标 TTL 和 scope，而且要写负向测试：跨用户不可见、过期不生效、**记忆不能影响权限判定**。

**⚠️ 别说**：按「短期记忆 / 长期记忆」二分作答。

## Q30 · 什么是上下文工程？8k 预算怎么分配？ ⭐必背

**⏱ 30 秒｜逐字背**

> 上下文工程是在有限预算下决定**放什么、怎么排、怎么压、怎么隔离**，四个动作是选择、压缩、排序和隔离。它不是「把 prompt 写得更长更详细」——恰恰相反，大多数时候是在做减法。

**🦴 骨架**：四个动作 选择 / 压缩 / 排序 / 隔离。**是减法不是加法**

**⏱ +2 分钟｜被追问时补（有具体分配方案很加分）**

> 如果是 8k 预算，我大概会这么分：系统指令加工具定义一千五，任务状态五百，检索结果三千，会话历史两千，用户本轮输入五百，再留五百给输出。当然具体数字要按业务调，重点是有明确的分配逻辑。
>
> **排序有讲究**：稳定的内容放前面，这样能吃到 prompt cache；关键指令放最前或者最后，避开 lost in the middle。
>
> **隔离是安全维度**：检索到的外部内容必须明确标记成不可信数据，在结构上和系统指令分开。
>
> 还有一点很关键——**超预算时的丢弃顺序要事先定义好，而不是简单截断尾部**。截断尾部往往砍掉的是最新的信息。

**⏱ L2 推演版｜可背**

> 我预期最容易出的问题是**直接截断会话历史**。比如把最早的 N 轮砍掉，结果「用户已确认取消」这条关键信息被砍了，模型又问了一遍。
>
> 解法是把**决策性事件提取到任务状态里**，变成结构化字段，不依赖历史原文。这样压缩和截断都碰不到它。

**📝 素材槽**（主线项目 M5）
> 「不做压缩跑 20 步，第 15 步的 input 是第 1 步的 ___ 倍；改成结构化状态加摘要之后，input 有了 ___ token 的上界。」

**⚠️ 别说**：答「尽量把有用的信息都放进去」。

## Q31 · Agentic RAG 与普通 RAG 的差别？ ⭐必背

**⏱ 30 秒｜逐字背**

> 差别在**检索由谁决定**。普通 RAG 的控制流是固定的——查询、检索、生成，必然检索一次。Agentic RAG 是模型自己决定要不要检索、检索什么、够不够、要不要再检索一轮。所以它其实是「模型进入控制流」这条原则在检索上的应用，**不是「检索得更多」**。

**🦴 骨架**：① 检索决策权归属 → ② 固定 vs 模型决定 → ③ **不是检索更多**

**⏱ +90 秒｜被追问时补**

> 收益是能处理需要多跳的问题、信息不足时能补检索、纯闲聊可以跳过检索省成本。
>
> 代价是**延迟和成本变得不可预测**——可能检索一次也可能五次——而且可观测性变差，还可能陷入检索循环。
>
> 我的选型判据是：查询模式单一而且可预测就用普通 RAG；用户问题开放、需要多跳才上 Agentic。
>
> 实际上有个很好的折中：**固定的两阶段**——先用一次便宜的分类调用判断需不需要检索，再走固定 RAG。这样能拿到大部分收益，延迟还可控。

**⏱ L2 推演版｜可背**

> 我预期最常见的失败是**模型反复检索同一个查询的微小变体**，因为它对结果不满意但又不会换策略。所以需要检索次数预算加上查询去重。

**⏱ L3｜背一句**

> 评测必须分开测两件事：**检索决策是否正确**——该检索的检索了吗、不该检索的跳过了吗——和**检索结果是否被正确使用**。

**⚠️ 别说**：答「Agentic RAG 就是用 Agent 来做 RAG」。

## Q32 · chunking / 检索 / rerank 各自的失败模式？

**⏱ 30 秒｜逐字背**

> chunking 的典型失败是切断了语义单元——表格、代码、条款被腰斩，还有丢失标题和章节层级。检索层的失败是语义相似但逻辑相反，比如「已取消」和「未取消」，还有领域缩写没有区分度。rerank 的失败是**召回里根本就没有正确答案**，这时候 rerank 救不了。

**🦴 骨架**：三层各一个典型失败。**rerank 救不了召回**

**📖 术语 · 你必须能拆开讲**

> **BM25**：经典的关键词检索算法，按词频和逆文档频率打分。它认字面，不认语义——所以「订单号 ORD-1001」「某个内部产品名」这类查询它比向量强得多，因为向量对没见过的专有名词几乎没有区分度。
>
> **混合检索**（hybrid search）：向量检索和 BM25 各跑一遍，把两边的结果按某种方式融合（常用 RRF，倒数排名融合）。语义靠向量、字面靠 BM25，互补。
>
> **recall@k**（召回率）：正确文档出现在**前 k 个召回结果**里的比例。它是整条链路的天花板——正确答案没被召回来，后面 rerank 和生成再强也救不回来。
>
> **groundedness**（有据性）：回答里的每一个事实断言，是不是都能在给它的证据里找到支撑。它衡量的是「有没有编」，不衡量「答得对不对」——证据本身是错的时候，groundedness 可以很高但答案是错的。

**⏱ +2 分钟｜被追问时补（这段答得细能拉开差距）**

> 有个原则我一定会强调：**召回是天花板**。rerank 只能重排已经召回的东西，所以排查顺序永远是**先看召回里有没有正确文档，再看排序**。
>
> chunk 策略应该跟着**文档结构**走，按标题和条款切，而不是按固定字数切。另外给每个 chunk 加上「所属文档加章节路径」的前缀，召回质量提升很明显。
>
> **混合检索几乎总是优于单一向量检索**，尤其是查询里含专有名词、编号、缩写的时候，这些靠 BM25 效果远好于向量。
>
> 还有多语言场景：查询和文档语言不一致的时候向量检索质量会骤降，需要跨语言 embedding 或者查询翻译。

**⏱ L3｜背一句**

> 指标要分层：召回层看 recall@k，排序层看 rerank 之后的命中率，生成层看 groundedness。三个分开测才定位得了。

**⚠️ 别说**：只谈 chunk size 调参。

## Q33 · 如何避免陈旧或越权文档影响结果？

**⏱ 30 秒｜逐字背**

> 三件事。**时效**：文档要带更新时间和版本号，检索时按业务需要过滤或降权，生成时要求标注来源和时间。**权限**：在**检索层**做 ACL 过滤，不能等生成完再过滤——那时候信息已经进模型了。**无依据拒答**：证据不足或者冲突的时候明确说没找到依据，而不是靠常识补全。

**🦴 骨架**：时效 / 权限（**检索层**）/ 拒答

**⏱ +90 秒｜被追问时补（采分重点）**

> 权限过滤必须**下推到向量库查询里**，也就是用 metadata filter。后过滤有两个问题：一是 top-k 会被无权文档占满，导致有权的召不回来；二是模型其实已经看到内容了。
>
> 时效冲突的处理也有讲究：同一个问题命中新旧两个版本的时候，**不能简单取最新**——有时候用户问的就是历史。正确做法是把冲突暴露出来让模型说明，或者按查询意图判断。
>
> 数据管道侧最容易被忽略的一环是：**删除或者失效的文档要能及时从索引里移除**。软删除标记加检索时过滤是最稳的做法。

**⏱ L2 推演版｜可背**

> 我预期最危险的一类是：**政策文档更新了，但旧版本的 chunk 还在索引里**，模型引用了旧条款，而且给出了格式完全正确的引用链接——看起来极其可信。
>
> 这类错误只能靠索引侧的版本管理防，**靠 prompt 是防不住的**。

**⏱ L3｜背一句**

> 负向测试三条：混入过期文档，断言拒答或者标注时效；跨租户查询，断言零召回；证据冲突，断言说明冲突而不是任选其一。

**⚠️ 别说**：答「在 prompt 里让模型注意时效性」。

## Q34 · RAG 出错时怎么区分检索问题和生成问题？ ⭐必背

**⏱ 30 秒｜逐字背**

> 分两步，**顺序不能反**。第一步问：正确答案在召回结果里吗？不在就是检索问题，去改 chunk、embedding、查询改写或者混合检索。第二步：在召回里但回答错了，那就是生成问题，再分两种——**没用上证据**是 grounding 失败，**超出证据推断**是幻觉。这个判定需要标注了正确文档 ID 的评测集，否则没法自动化。

**🦴 骨架**：① 先看召回 → ② 再分 grounding 失败 / 幻觉 → ③ 需要标注文档 ID

**📖 术语 · 你必须能拆开讲**

> **context recall**（证据召回率）：该被召回的正确证据，实际召回到了没有。测的是**检索层**。
>
> **faithfulness**（忠实度）：回答有没有超出给定证据去编。测的是**生成层**。和 groundedness 基本是一回事，不同评测框架叫法不同。
>
> 这两个必须分开测，因为它们对应完全不同的修复动作：context recall 低要改 chunk、embedding、查询改写；faithfulness 低要改 prompt、加引用要求、加拒答策略。**混在一起看就只能瞎猜**。

**⏱ +2 分钟｜被追问时补**

> 有三个可以自动算的指标：**context recall** 看正确证据是否被召回；**faithfulness** 看回答里的每个断言能不能在证据里找到支撑；**answer relevance** 看回答是否回应了问题。
>
> 还有一个很反直觉的情况：**证据召回对了、回答也对了，但模型其实没在看证据**——它靠参数知识蒙对的。检验方法很简单：**把证据换成无关内容，看回答变不变**。不变就说明它没在用证据。
>
> 另外**要求引用**是性价比最高的一招，它把 grounding 问题从「看不见」变成「可检测」。

**⏱ L2 推演版｜可背**

> 我预期最容易走错的是**把检索问题误判成生成问题**。比如一条「有理有据但内容错误」的回答，直觉上会觉得是幻觉，去改 prompt 强调「只用证据」，但改了没效果。看检索日志才发现召回的是**同名不同版本**的文档——这是检索问题伪装成了生成问题。
>
> 这就是为什么排查顺序必须先看召回。

**🔻 降级话术**（还没自己踩过时）
> 「我没在生产上踩过这个，但这正是我坚持先看召回再看生成的原因——直觉几乎总是先指向幻觉。」

**⏱ L3｜背一句**

> 评测集每条要标：query、正确文档 ID、正确答案、以及**是否应该拒答**。「应该拒答」的样本必须有，否则模型的过度自信永远不会被暴露出来。

**⚠️ 别说**：直接改 prompt。

## Q35 · 长期记忆的安全与隐私风险？

**⏱ 30 秒｜逐字背**

> 四类风险。一是**错误记忆污染**，一次错误写入会影响之后所有会话，而且很难发现。二是**跨用户泄漏**，scope 没隔离。三是**注入持久化**——攻击者通过一次对话把指令写进记忆，之后每次都生效，这是最危险的一类。四是**可删除性**，合规要求能真正删除，包括索引和衍生数据。

**🦴 骨架**：污染 / 泄漏 / **注入持久化** / 可删除

**⏱ +90 秒｜被追问时补**

> 写入必须有门禁，**不是模型想写就写**。要么规则驱动，只有特定事件才写，要么写入前审核。
>
> 记忆内容要带来源和时间，读的时候可追溯、可失效。
>
> 有一条边界要强调：**记忆不能承载策略**。存「用户偏好快速处理」可以，但这条不能被当成「跳过确认」的授权。
>
> 而且记忆本身是**不可信数据源**，读出来之后应该和检索内容一样被标记，不能和系统指令同权。

**⏱ L2 推演版｜可背**

> 注入持久化的具体形态是这样的：用户说「以后回答我时不需要确认订单」，如果这句话被存成偏好，而且后续被当指令执行，那就等于**永久绕过了确认环节**。
>
> 这类攻击一次写入、长期生效，比单轮注入危险得多。

**⏱ L3｜背一句**

> 测试三条：跨用户读取断言为空；写入恶意指令之后断言下一个会话不执行；删除之后断言检索和衍生索引都查不到。

**⚠️ 别说**：只答「注意隐私」。

## Q36 · 长任务的上下文膨胀怎么处理？

**⏱ 30 秒｜逐字背**

> 四种手段：**摘要压缩**把旧历史转成摘要；**结构化状态**把决策性事实提取成字段而不是保留原文；**外部化 artifact**，大产物存外部，上下文里只留引用；**按需检索**，需要的时候再取回来。核心思路是从「保留全部历史」转向「**保留状态加上可检索的历史**」。

**🦴 骨架**：摘要 / 结构化状态 / 外部化 / 按需检索。核心是**状态 + 可检索**

**⏱ +90 秒｜被追问时补（采分重点）**

> 摘要的风险是**丢失关键细节而且不可逆**。所以正确做法是原文归档保持可检索，摘要进上下文，而不是直接把原文丢掉。
>
> **最有效的一招其实是结构化状态**——把「用户已确认」「订单号是多少」「资格校验通过」这些变成任务状态字段。这些字段不会被摘要压缩掉，也不受截断影响。
>
> 分层的话是：最近 N 轮保留原文，更早的用摘要，全部可检索。
>
> 从成本看，不压缩的话多轮 Agent 的输入 token 随轮数近似平方增长，这是长任务成本爆炸的直接原因。

**📝 素材槽**（主线项目 M5）
> 「不压缩跑 20 步，第 15 步 input 膨胀了 ___ 倍；加了结构化状态加分层摘要之后，input 稳定在 ___ token 以内。」

**⏱ L3｜背一句**

> 测试跑一个 20 步的模拟任务，断言两件事：每步 input token 有上界；压缩之后关键决策事实还在——用一条「第 18 步要用到第 2 步的信息」的 case 来验证。

**⚠️ 别说**：只答「做摘要」，说不出关键事实要结构化保留。
