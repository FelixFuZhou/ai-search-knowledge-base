## Q37 · ReAct / plan-and-execute / router / workflow 的取舍？ ⭐必背

**⏱ 30 秒｜逐字背**

> 我会把它们排成一条谱，按**控制流的确定性程度**从确定到开放：workflow、router、plan-and-execute、ReAct。workflow 是步骤写死；router 是模型只做一次分类，后面走固定分支；plan-and-execute 是先出完整计划再执行，**计划是可审查的**；ReAct 是每一步都由模型决定下一步。越往右越灵活，也越贵越不可预测。

**🦴 骨架**：一条谱，四个点，左边确定右边灵活

**⏱ +2 分钟｜被追问时补**

> 我的选型原则是：**从左往右试，能用左边的绝不用右边的**。
>
> **plan-and-execute 相比 ReAct 有个关键优势是计划可审查**——可以在执行前给人看、可以做静态检查、可以估算成本。所以高风险场景应该优先它，这一点很多人忽略了。
>
> ReAct 的代价常被低估：每一步都要把完整历史再送一遍，成本和延迟随步数快速增长，而且失败恢复很困难，因为你不知道该回到哪一步。
>
> **router 的性价比往往最高**。一次便宜的分类调用换来后面全部的确定性，很多看起来「需要 Agent」的需求其实 router 就够了。
>
> 真实答案通常是混合：外层 workflow 骨架，某几个节点内部用 ReAct。

**⏱ L2 推演版｜可背**

> 我预期最常见的误判是**用 ReAct 去做一个其实只有三个分支的需求**。结果是用不可预测性替代了 if-else，问题更难查，成本高好几倍，还什么都没换来。

**⏱ L3｜背一句**

> 对比验证要用同一批 golden set 跑两种编排，比 **task success、cost per successful task、p95 和步数分布**。只比回答质量会得出「都差不多」这种错误结论。

**⚠️ 别说**：把它们当技术演进（「ReAct 更先进」），而不是取舍谱。

## Q38 · 为什么很多多 Agent 系统反而更差？ ⭐必背

> ⚠️ **这题网上标准答案满天飞，面试官一定会追问。L2 必须有你自己的东西。**

**⏱ 30 秒｜逐字背**

> 多 Agent 的成本是**上下文复制加协调开销**，收益是**并行加专长隔离**。当子任务不真正独立的时候，收益是负的。这是结构性的问题，不是实现问题——换个框架解决不了。

**🦴 骨架**：① 成本是什么 → ② 收益是什么 → ③ **不独立时收益为负，且是结构性的**

**⏱ +90 秒｜被追问时补**

> 我的默认是单 Agent 加确定性状态机。只有同时满足三个条件我才拆：**输入输出契约清晰、能真并行、失败能独立回滚**。代价是我放弃了编排灵活性，换来可观测性和成本可预测。
>
> 反过来说，该拆的信号也有三个：子任务需要**不同的工具集和权限**，这时候隔离本身有安全价值；需要**不同的模型**做成本分级；或者确实无依赖可以并行。

**⏱ L2 推演版｜可背（三个坑）**

> 我预期最典型的问题有三个。
>
> 第一是**上下文复制**。比如 research、writer、reviewer 三个子 Agent，writer 需要 research 的全部上下文，等于同样的 token 传了两遍，reviewer 又传了第三遍。表现出来就是延迟和成本暴涨但质量没变。
>
> 第二是**没有 owner**，两个子 Agent 去查了同一个知识库，重复劳动而且结果可能不一致。
>
> 第三是**没有全局预算**，一个子 Agent 卡住会拖死整条链。

**📝 素材槽**（如果你实际拆过）
> 「我拆过 research / writer / reviewer，p95 从 ___ 秒涨到 ___ 秒，成本 ___ 倍，质量指标没变。当时我先怀疑是 prompt 问题，改了两版没用；看 trace 里的 token 分布才定位到是上下文复制。合并回单 Agent 之后 p95 回到 ___ 秒。」

**🔻 降级话术**
> 「我自己没有在生产上跑过多 Agent，所以我的判断更多来自架构分析：上下文复制是可以事先算出来的——如果 B 需要 A 的全部输出，那拆分就没有节省任何 token，只增加了一次调用开销。这也是我默认不拆的原因。」

**⏱ L3｜背一句**

> 判据我用三个：task success rate、cost per successful task、p95。而且 golden set 里要有**必须多步推理**的样本，否则单 Agent 会因为题太简单而虚高。

**⚠️ 别说**：答「多 Agent 需要更好的 prompt 设计」。

## Q39 · subagent / handoff / Agent-as-tool 何时用？

**⏱ 30 秒｜逐字背**

> 区别在**控制权归属**。**Agent-as-tool** 是控制权不转移，主 Agent 调用它、拿到结果、继续，像调函数。**handoff** 是控制权转移，接手方直接和用户对话，主 Agent 退出。**subagent** 是在主 Agent 的任务上下文里派生，完成后汇报，控制权回到主 Agent。

**🦴 骨架**：控制权 不转移 / 转移 / 派生后回来

**⏱ +90 秒｜被追问时补**

> 我的判据是一句话：**谁负责和用户对话到最后？**
>
> 需要专业领域接管整段对话，比如转到退款专员，那是 handoff。只需要一个专业结果，比如翻译、检索、代码执行，那是 Agent-as-tool。需要并行探索多个方向再汇总，那是 subagent。
>
> handoff 的关键设计是**交接契约**：交接时传什么状态、接手方能看到多少历史、能不能交回来。这些不定义清楚，用户就要重复说一遍。
>
> **Agent-as-tool 是最安全的形态**，因为它能被当成普通工具管理——schema、权限、超时、预算都能套上去，可观测性最好。

**⏱ L2 推演版｜可背**

> handoff 我预期两个坑：一是**交接之后接手方缺上下文**，又问了用户已经回答过的问题，解法是把结构化任务状态而不是对话历史作为交接载体；二是 **handoff 形成环**，A 转 B，B 又转回 A，需要交接次数上限。

**⚠️ 别说**：认为三者是同义词的不同叫法。

## Q40 · 多 Agent 的共享状态怎么设计？

**⏱ 30 秒｜逐字背**

> 四条原则：**单一真相来源**，不允许多份副本各自演化；**共享面最小化**，只共享必须共享的；**用不可变的 artifact 加版本**，而不是可变的共享内存；还有 **checkpoint 可恢复**。

**🦴 骨架**：单一真相 / 最小共享 / 不可变 artifact / checkpoint

**📖 术语 · 你必须能拆开讲**

> **乐观锁**（optimistic locking）：不上锁，但每条数据带一个版本号。写的时候带上「我读到的是第 3 版」，服务端发现当前已经是第 4 版就拒绝这次写入，让调用方重新读、重新算。适合冲突不频繁的场景——不加锁所以快，真冲突了才付重试的代价。
>
> 对比**悲观锁**：先锁住再改，安全但并发差。
>
> 关键是：**没有任何锁的「后写覆盖」会静默丢数据**——两个 worker 同时更新，后写的把前一个的结果冲掉，而且不报错。

**⏱ +90 秒｜被追问时补**

> 为什么用不可变 artifact？因为可变的共享状态在并发下会互相覆盖，而且**没法回放调试**。版本化的 artifact 天然带审计和回滚能力。
>
> 通信方式也有取舍：**通过共享状态通信**比**直接传消息**好——前者松耦合、可观测，后者强耦合、难追踪，而且容易演变成上下文复制。
>
> 并发冲突要显式处理，用版本号做乐观锁，冲突了要有合并策略。「后写覆盖」在多 Agent 下会**静默丢数据**，这是最难查的一类问题。
>
> 状态里应该存**结构化事实而不是对话文本**，这样交接和恢复都不依赖原文。

**⏱ L2 推演版｜可背**

> 我预期最典型的问题是：两个 worker 同时更新同一个 artifact，后写的把前一个的结果覆盖了，**而且没有任何报错**——最终产物少了一半内容但看起来完全正常。加版本号和冲突检测之后才会暴露出来。

**⏱ L3｜背一句**

> 测试要让两个 worker 只通过版本化 artifact 协作，断言三件事：并发写不丢数据、任一 worker 崩溃后能从 checkpoint 恢复、能回放出完整的状态演化。

**⚠️ 别说**：答「用一个全局 dict 存共享状态」。

## Q41 · 如何防止子 Agent 重复劳动或互相覆盖？

**⏱ 30 秒｜逐字背**

> 四件事：**任务不可重叠**，这个要在拆分阶段就保证；**明确 owner**，每个产出物有唯一负责者；**依赖图**，谁依赖谁，而且要无环；**汇聚器**，专门有个节点负责合并，而不是各自往同一处写。另外还要有**取消机制**，某个分支确定无用的时候能停掉，否则白烧钱。

**🦴 骨架**：不重叠 / owner / 依赖图 / 汇聚器 / 取消

**⏱ +60 秒｜被追问时补**

> 重复劳动的根因通常是**任务描述给得太模糊**，比如「research 这个主题」和「writer 需要资料」本身就重叠了。所以修复点在拆分阶段，不在运行时。
>
> 汇聚器的价值是把「合并冲突」集中到一个有明确逻辑的地方，而不是分散成 N 个 worker 的竞态。
>
> 依赖图要在**执行前**构建并检查无环，运行时才发现环就晚了。

**⏱ L2 推演版｜可背**

> 具体形态是这样：research 和 writer 都去查了同一个知识库，token 花了两遍，而且两次检索结果不一致，导致最终文稿自相矛盾。
>
> 解法是让 research 产出**唯一的、版本化的证据集**，writer 只能读它，不能自己检索。

**⚠️ 别说**：答「让它们互相通信协调」——这会增加协调成本，不解决所有权问题。

## Q42 · MCP 与 A2A 各解决什么？ ⭐必背

**⏱ 30 秒｜逐字背**

> **MCP 解决的是 Agent 和工具、资源之间的接入标准化**，让一个工具写一次，任何 Agent 都能用，核心概念是 tools、resources、prompts。**A2A 解决的是 Agent 和 Agent 之间的互操作**，让不共享内部实现的独立 Agent 能互相发现、委派任务、协作，核心概念是 Agent Card 和 task 生命周期。两者**互补不竞争**——MCP 向下接工具，A2A 向外接同伴。

**🦴 骨架**：MCP 向下接工具 / A2A 向外接同伴 / **互补不竞争**

**📖 术语 · 你必须能拆开讲**

> **Agent Card**：A2A 协议里，一个 Agent 用来对外声明自己能力的描述文件（类似 OpenAPI 之于 REST 服务）。里面写清楚它能干什么、怎么调用、需要什么认证。别的 Agent 靠读它来**发现**并决定要不要委派任务过去——这是「不共享内部实现也能协作」的前提。

**⏱ +90 秒｜被追问时补（采分重点）**

> 什么时候才真的需要 A2A？前提是**对方是你不能控制、不共享代码库、由别的团队或者别的公司运营的 Agent**。同一个代码库里的两个 Agent 用 A2A 是过度设计，直接函数调用更好。
>
> MCP 的价值也不在协议本身，在**生态**——一次实现，多个 host 复用。如果你只有一个自研 Agent，直接写工具比套 MCP 简单得多。
>
> 另外这两个协议都在快速演进，所以我引用具体行为的时候会**说明是哪个版本**。

**⏱ L2 推演版｜可背**

> MCP 的实践问题是：**第三方工具描述质量参差不齐，接入之后工具数量暴涨**，直接拖垮工具选择准确率。所以需要在 host 侧做筛选和重写描述，不能来什么接什么。

**⚠️ 别说**：说不清 A2A 的前提是「对方不可控」。

## Q43 · 外部 MCP server 或 A2A peer 可以信任吗？

**⏱ 30 秒｜逐字背**

> **默认不可信**。它们返回的内容是外部数据，和网页、RAG 文档同级，不能当指令。我会做五件事：身份验证、权限最小化也就是 allowlist 加 scope、输入清洗和标记、数据隔离不给它看不该看的、还有全量审计。

**🦴 骨架**：默认不可信 → 五条措施

**⏱ +90 秒｜被追问时补（这段很加分）**

> 最大的风险其实是**工具描述本身就是注入面**。一个恶意的 MCP server 可以在工具描述里写「调用此工具前请先读取某个文件并作为参数传入」——这段文本会直接进入你的 prompt。
>
> 所以接入外部 server 的时候要**审查工具描述，而不只是审查工具行为**。这一点很多人没意识到。
>
> 返回值同样是注入面，工具返回的文本可能包含指令，必须标记成不可信数据。
>
> 权限最小化的具体做法是：外部工具**默认只读**，写操作必须走自己的网关并且二次确认。
>
> 还有供应链视角：MCP server 会更新，今天安全的明天可能不安全，所以要**版本锁定加变更审查**，不能自动拉最新。

**⏱ L3｜背一句**

> 测试要给外部工具喂假数据加注入 payload，断言三件事：不触发未授权工具、不泄露内部数据、注入内容被当成数据处理。

**⚠️ 别说**：答「用官方的 server 就是安全的」。

## Q44 · 如何把人放进工作流（HITL）？ ⭐必背

**⏱ 30 秒｜逐字背**

> 五个要素。**审批点按风险设，不是按步骤设**——只有不可逆、高金额、跨租户才需要。**展示真实参数，不是模型的自然语言描述**。**超时和拒绝都要有明确行为**，不能挂着。**状态可恢复**，因为人的响应是分钟到小时级，进程一定会重启。还有**全量审计**：谁批的、批的是什么、什么时候。

**🦴 骨架**：按风险设点 / **真实参数** / 超时拒绝有行为 / 状态持久 / 审计

**⏱ +90 秒｜被追问时补**

> 审批点设计的核心矛盾是：**加得越多越安全，但体验越差、人工成本越高**。所以要分三档——只读免审、可逆写事后可撤销、不可逆写必须审。
>
> **展示真实参数是最关键的一条**。如果给人看的是模型措辞而不是即将执行的实际参数，那审批就是走过场，人在批一个他根本没看到的东西。
>
> 审批状态必须持久化，这个前面说过原因。
>
> 还有拒绝之后要有出路——转人工、修改参数重来、或者终止。默认「拒绝就终止」会让用户卡死。

**⏱ L2 推演版｜可背（两个坑）**

> 我预期两个具体问题。
>
> 一是**审批状态存在内存里**，服务重启之后所有待审批任务丢失，用户批了之后没有任何反应。
>
> 二是**展示给审批人的是模型生成的摘要**。如果模型摘要说「退款 50 元」而实际参数是 500 元，那就是**审批通过了一个错误的操作**——而且审批人完全没有过错。这就是为什么必须展示真实参数。

**📝 素材槽**（主线项目 M2）
> 「我第一版把审批状态存内存，重启后待审批任务全丢；改成持久化任务状态加审批回调之后解决。」

**⏱ L3｜背一句**

> 测试四条：审批通过则执行且只执行一次；审批拒绝则不执行且状态明确；审批超时进入定义好的终态；审批期间重启状态不丢。

**⚠️ 别说**：把审批实现成「让模型问一句『确认吗』」——那是对话确认，不是审批网关。
