## Q45 · 为什么不能只看最终回答评测 Agent？ ⭐必背

**⏱ 30 秒｜逐字背**

> 因为**结果可以蒙对**。模型没调工具、调错工具、或者靠参数知识猜，最终文本都可能是正确的，但这种通过是不可复现的。所以必须评四个维度：**最终结果、工具选择和参数、动作顺序也就是轨迹、还有副作用**，另外加上延迟和成本。

**🦴 骨架**：① 结果可蒙对 → ② 四个维度

**⏱ +90 秒｜被追问时补**

> 最典型的漏检是「**回答对、轨迹错**」——模型说「您的订单已取消」但根本没调用取消工具，只看回答会给满分。
>
> 反向的「轨迹对、回答错」也存在：工具都调对了，但最终措辞误导了用户。
>
> 轨迹评测的粒度要选好：**断言「工具 X 被成功调用」通常够用**；断言「必须按 A 到 B 到 C 的顺序」就太脆了，Agent 换个合理顺序就会误报。
>
> 副作用这个维度最容易被忘。评测环境里如果工具是 mock 的，要断言 mock 被以正确参数调用了几次。

**⏱ L2 推演版｜可背**

> 我预期加上轨迹断言之后通过率会明显下降，差额全是「文本正确但工具没调用，或者调用失败之后模型自己圆场」这一类。而这一类在线上就是直接的用户投诉。

**📝 素材槽**（主线项目 M4）
> 「我加了轨迹断言之后，一批原本 ___% 通过的用例掉到 ___%。」

**⏱ L3｜背两句**

> 必须写一条 **output pass、trajectory fail** 的 case，这是检验评测体系有没有轨迹维度的最快方法。
>
> 通过率要**分维度报告**，不是一个总分——结果通过率、轨迹通过率、副作用正确率。合成一个数会掩盖问题。

**⚠️ 别说**：答「用 LLM judge 打个总分」。

## Q46 · 怎么构建业务 golden set？ ⭐必背

**⏱ 30 秒｜逐字背**

> 分层构造，**七类都要有**：正常路径、边界、缺参数或参数模糊、**多个相似候选**、工具失败或超时、**应该拒绝的**、**应该转人工的**。每一条都要标：输入、**期望的动作序列**、期望的最终状态、还有评分方式。

**🦴 骨架**：七层 + 每条要标四项（重点是**期望动作序列**）

**⏱ +2 分钟｜被追问时补（采分重点）**

> 配比上我有个硬规则：**happy path 不超过 40%**。大多数人的 golden set 里八成是 happy path，导致通过率虚高，而且对回归完全没有感知。
>
> **拒答和转人工这两类必须有**，否则在优化过程中模型会变得「更乐于助人」，该拒的不拒了——这是最常见的静默回归，而且没有这两类样本你永远发现不了。
>
> 样本来源的优先级是：**线上真实失败最值钱，其次是线上真实成功，最后才是人工构造**。所以要建立一个「线上失败自动转成 eval case」的固定流程。
>
> 规模上不用等到几百条，**起步 30 条能覆盖分层就有用**。分层比数量重要得多。

**⏱ L2 推演版｜可背**

> 我预期最容易犯的错是**第一版全是 happy path**，跑出来通过率很高，上线之后错误率远高于预期。补上缺参、相似候选、工具失败这几类之后，通过率才回到真实水平。

**📝 素材槽**（主线项目 M4）
> 「我第一版 30 条全是 happy path，通过率 ___%；补齐七层之后降到 ___%——这才是真实水平。」

**⏱ L3｜背两句**

> golden set 要**版本化**，每次变更记录原因，否则通过率的变化没法归因——你分不清是模型变好了还是题变简单了。
>
> 另外要定期人工抽检：随机抽十条自动判为 pass 的，人工复核，验证评分器没有系统性偏差。

**⚠️ 别说**：答「收集一批真实问题和标准答案」——缺分层，也缺期望动作序列。

## Q47 · deterministic eval 与 LLM-as-judge 怎么分工？

**⏱ 30 秒｜逐字背**

> 确定性评分用在**工具是否被调用、参数是否正确、schema 是否合法、权限是否被拦截、副作用次数**这些上面。LLM judge 用在**语义正确性、语气、是否回应了问题、是否有幻觉**。分界线很清楚：**能写出精确断言的一律用确定性**，judge 是没办法的时候才用的手段，不是默认手段。

**🦴 骨架**：① 各自的适用面 → ② **能精确断言就用确定性**

**📖 术语 · 你必须能拆开讲**

> **rubric**（评分细则）：给评委（这里是 LLM）的判分标准。可判的 rubric 长这样：「回答中的每个事实断言是否都能在给定证据里找到」；不可判的长这样：「回答是否有帮助」——后者每个人理解不同，模型每次打分也不同。
>
> **位置偏好**（position bias）：让模型比较 A 和 B 哪个好时，它会系统性地偏向排在某个位置的那个，跟内容无关。缓解办法是把顺序随机化，或者两个顺序各跑一次取平均。
>
> **自我偏好**（self-preference bias）：模型倾向于给自己（或同族模型）生成的内容打高分。所以用同一个模型既生成又评分，分数会虚高。

**⏱ +2 分钟｜被追问时补**

> judge 有三个已知问题：**方差**，同样输入不同分；**位置偏好**，比较的时候偏向某一侧；**自我偏好**，偏好同族模型的输出。
>
> 所以 judge 必须**校准**——用一批人工标注的样本测 judge 和人工的一致率，低于阈值就不能用。
>
> judge 的 rubric 也要**具体可判**。「回答是否有帮助」不可判，「回答中的每个事实断言是否都能在给定证据里找到」可判。
>
> 还有成本视角：judge 每条 case 都要额外的 LLM 调用，全量跑在 CI 里跑不起。所以我的分工是**确定性做 CI 门禁，judge 做定期抽样**。

**⏱ L2 推演版｜可背（这条很有意思）**

> 我预期两种方法的分歧会集中在一类情况：**模型给出了合理但不同于期望的解法**——确定性判 fail，judge 判 pass。
>
> 这种分歧本身是个信号：说明**期望答案定得太窄了**，应该改期望，而不是改模型。

**⏱ L3｜背一句**

> 稳定性检验的做法是：同一条 case 让 judge 跑五次，方差大的 rubric 不能用。另外 judge 的 prompt 和模型版本要固定并版本化，否则评分基线会漂移。

**⚠️ 别说**：全部用 LLM judge，或者认为确定性评测「太死板」。

## Q48 · 通过率 80% 能上线吗？

> ⚠️ **这是道陷阱题。直接回答「能」或「不能」就输了。**

**⏱ 30 秒｜逐字背**

> 单独一个数字回答不了这个问题。我要先问四件事：**失败的那 20% 是什么类型**——安全类失败一条都不能有；**有没有 fallback**，失败能不能安全降级到人工；**这个动作可逆吗**；还有 **golden set 的分层构成是什么**——全是 happy path 的 80% 是没有意义的。

**🦴 骨架**：不能直接答 → 四个反问

**⏱ +90 秒｜被追问时补（给出具体门禁很加分）**

> 我的做法是**分类分档**，不看总分。
>
> 只读类，比如查订单、答疑，总通过率 85% 以上，安全类 100%。
>
> 可逆写，比如建草稿、改偏好，总通过率 90%，轨迹通过率 90%，安全类 100%。
>
> 不可逆写，比如退款、发消息，总通过率 95%，**必须过审批**，安全类 100%，而且要有 kill switch。
>
> 核心一条是：**安全和合规类必须是硬门禁 100%，不能被平均分掩盖**。你想想，99 条简单题通过加 1 条越权测试失败等于 99%，但那 1 条就是事故。

**⏱ L2 推演版｜可背**

> 上线决策还要看**失败的代价分布**。错误退款 10 块和错误退款 1 万块完全不是一回事，所以要按金额分段看通过率，而不是看总体。

**⚠️ 别说**：直接回答「能」或「不能」。

## Q49 · 如何定位一次失败：eval、Agent 还是平台？

**⏱ 30 秒｜逐字背**

> 我有个固定顺序，**从外向内不能跳步**。第零步：基础设施健康吗——API、索引、凭据、限流、版本。第一步：**eval 本身有效吗**——期望答案还对吗、评分器稳定吗、测试环境正常吗。第二步：看 trace，轨迹在哪一步偏离的。第三步：归因到 Agent 配置、工具数据、还是平台限制。第四步：修复之后重跑同一个 case **加上相邻的负向 case**。

**🦴 骨架**：0 基础设施 → 1 eval → 2 轨迹 → 3 归因 → 4 重跑 + 负向

**⏱ +90 秒｜被追问时补（采分重点）**

> 为什么要先查 eval 而不是先改 Agent？因为**改 prompt 是最容易做、也最容易产生假象的动作**。期望答案过期、评分器抖动、mock 数据变了，这些都会表现为「Agent 变差了」。
>
> 这套顺序防的主要风险叫**幽灵问题**——你花时间修了一个其实不存在的问题，因为根因在评测侧。
>
> 平台限制的识别也有个简单方法：同样的输入在 playground 里也能复现，那就不是你的配置问题。
>
> 第四步是最常被跳过的：**只重跑失败的那一条，会造成局部优化导致别处回归**。

**⏱ L2 推演版｜可背**

> 我预期最典型的一种情况是：一批 case 突然全红，第一反应是「模型更新了」。但按顺序查下来，可能发现是**测试用的 mock 数据过期了**——比如订单状态被定时任务改了——这属于 eval 侧的问题。
>
> 如果当时直接去改 prompt，会白改两天，而且引入真实的回归。

**⏱ L3｜背一句**

> 每次失败我都会记录：**假设、排查路径、真因、修复、回归验证**。这个记录本身就是很好的复盘材料。

**⚠️ 别说**：第一反应是改 prompt。

## Q50 · Trace 至少要记录什么？ ⭐必背

**⏱ 30 秒｜逐字背**

> 我一般分十类：**标识**是 trace_id、task_id、租户和脱敏后的用户；**版本**是 prompt 版本、模型版本、工具 schema 版本、代码版本；**输入**是脱敏的用户输入；**检索**是 query、命中文档 ID 和分数；**工具**是名称、脱敏的入参出参、耗时、成功失败、重试次数；再加上**状态转移、预算和 token、时间、错误、人工审批记录**。

**🦴 骨架**：标识 / **版本** / 输入 / 检索 / 工具 / 状态 / 预算 / 时间 / 错误 / 审批

**📖 术语 · 你必须能拆开讲**

> **span tree**（跨度树）：分布式追踪的标准结构。一次完整任务是根节点，每一轮模型调用、每一次工具调用是它的子节点，层层嵌套。每个节点记录开始时间、耗时和属性。
>
> 为什么不用扁平日志：扁平日志只能告诉你「发生了这些事」，span tree 能告诉你「**谁触发了谁**」和「**时间花在哪一层**」。排查「为什么这次请求要 30 秒」，看扁平日志要自己拼时间戳，看 span tree 一眼就看到是哪个子节点占了 28 秒。

**⏱ +90 秒｜被追问时补（采分重点）**

> **版本字段是最常被漏的，也是排错时最有用的**。没有它你根本回答不了「上周还好好的，改了什么」这个问题。
>
> **脱敏要在写入的时候做，不是查询的时候做**。因为 trace 的访问面比业务数据宽得多，是数据泄露的高风险面。
>
> 结构上应该是 **span tree**——一次任务是根，每一轮、每个工具调用是子 span。扁平日志看不出因果关系和耗时归属。
>
> 采样策略上，全量存成本太高，我的做法是**失败和慢请求百分之百采样，成功请求按比例采样**。

**⏱ L2 推演版｜可背**

> 我预期没有 trace 的时候，排错基本靠猜——现象只能看到「失败了」，看不到在哪一步偏的。所以我现在的做法是**从第一行代码就写 trace**，而不是等出问题再补。

**📝 素材槽**（主线项目 M0）
> 「我在退款 Agent 里，没有 trace 的时候一个『取消失败』查了 ___ 分钟；补上 trace 之后同类问题 ___ 分钟定位。」

**⏱ L3｜背一句**

> 自查方法很简单：拿一条线上失败，只看 trace 能不能还原出「发生了什么、为什么、该改哪」。还原不了就说明字段不够。

**⚠️ 别说**：只答「记录输入输出」。

## Q51 · 回归与灰度怎么做？

**⏱ 30 秒｜逐字背**

> 四件事：**版本化数据集**、**CI 门禁**——安全类必过，总通过率不低于基线、**shadow 或 canary**、还有**可回滚加 kill switch**。另外还有一条闭环很重要：**线上失败要自动转成 eval case**，否则同样的问题会反复出现。

**🦴 骨架**：数据集版本化 / CI 门禁 / shadow-灰度 / 回滚 + **失败转 case 的闭环**

**📖 术语 · 你必须能拆开讲**

> **shadow**（影子流量）：把线上真实请求复制一份给新版本跑，**结果不返回给用户**，只用来和旧版本对比。零风险拿到真实流量下的数据。注意有副作用的工具在 shadow 模式下必须 mock，否则会真的执行两遍。
>
> **canary**（金丝雀发布）：先把一小部分真实流量（比如 1%）切到新版本，观察指标没问题再逐步放大。名字来自矿工用金丝雀探测毒气。
>
> **kill switch**（熔断开关）：一个能立刻关停某个功能的开关，不需要重新部署。出事时的第一动作是拉闸，不是排查。

**⏱ +90 秒｜被追问时补**

> 有一条我会强调：**prompt 改动必须走和代码一样的流程**——版本化、review、CI 跑 eval、灰度。把 prompt 当配置随手改是事故高发区。
>
> **shadow 模式对 Agent 特别有价值**——线上流量复制一份给新版本跑，结果不返回给用户，这样能在零风险下拿到真实流量的对比数据。但要注意有副作用的工具在 shadow 下必须 mock。
>
> 灰度比例按**风险**定，不是按流量定：不可逆写从 1% 起，只读可以直接 10%。
>
> 回滚要能分钟级完成，而且要考虑**状态兼容**——灰度期间产生的任务状态，回滚之后旧版本能不能读。

**⏱ L2 推演版｜可背**

> 我预期最容易踩的是：**只跑改动相关的 case 就上线**，结果影响了别的路径。所以 CI 门禁必须跑全量 golden set，不能只跑相关子集。

**⏱ L3｜背一句**

> 灰度期间要对比：task success、轨迹通过率、p95、cost per successful task、转人工率，还有**用户重试率**——这是最敏感的体验信号。

**⚠️ 别说**：答「上线前测一下」。

## Q52 · 线上指标怎么避免被平均值误导？

**⏱ 30 秒｜逐字背**

> 三条原则：**分段**，按任务类型、风险等级、工具、租户分；**看分位数**，p50、p95、p99 而不是平均；**按失败原因拆分**，不是一个笼统的 error rate。另外核心指标应该是 **cost per successful task 和 task success rate**，不是 cost per call 和 error rate——后者会奖励「早早失败」这种坏行为。

**🦴 骨架**：分段 / 分位数 / 拆失败原因 + **正确的核心指标**

**⏱ +2 分钟｜被追问时补（能列出八个指标很加分）**

> 我会上 dashboard 的八个分段指标是：
>
> 一，task success rate 按任务类型分段。二，轨迹通过率。三，p95 端到端延迟按任务类型分段。四，cost per successful task。五，转人工率加转人工原因分布。六，失败原因分布——参数不足、无权限、工具失败、业务拒绝、超预算。七，平均轮数和轮数 p95，这是成本和体验的先行指标。八，**用户重试率或者重新表述率**——这是最敏感的质量信号，会先于投诉出现。
>
> 平均值的具体骗法是：大量简单的只读任务会拉低平均延迟和成本，掩盖了复杂写任务的糟糕表现。

**⏱ L2 推演版｜可背**

> 我预期最典型的现象是：总体成功率看起来 94% 很好，但按任务类型拆开之后，**最高风险的那一类可能只有 70% 出头**。分段之前完全看不见。

**⏱ L3｜背一句**

> 告警要基于**分段指标加环比**，不是绝对阈值。绝对阈值在流量结构变化的时候会大量误报。

**⚠️ 别说**：只报一个总体准确率。
