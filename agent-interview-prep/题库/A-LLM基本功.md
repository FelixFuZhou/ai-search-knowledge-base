# 模块 A：LLM 基本功（Q01–Q10）

> **定位**：电话轮 / 暖场 / 现场热身。答不出直接挂，答得漂亮也加不了多少分——所以目标是**60 秒内干净利落答完，不纠缠**。
>
> **本模块只需 L0 + L1，不需要 L2/L3。**
>
> 下面写的是**采分点**（判卷标准），不是给你背的答案。用自己的话组织，出声计时。

## Q01 · token 与 tokenizer：为什么 token 数不等于字数？ <a id="q01"></a>

**考察点**：你有没有真的算过成本，还是只在 API 层面用过。

**L0 采分点**
- tokenizer 把文本切成子词单元（BPE / SentencePiece 一类），token 是模型的最小输入单位
- 英文常见词 ≈ 1 token，**中文常见 1 字 ≈ 1–2 token**，罕见字/emoji 更多
- 代码、JSON、URL 的 token 密度差别很大——大量括号和缩进会显著抬高 token 数

**L1 采分点**
- 工程影响三条：**成本估算**（不能用字数近似）、**context 预算**（截断位置要按 token 算）、**结构化输出**（JSON 的 key 名越长越贵，字段名应短）
- 不同模型 tokenizer 不同，同一段文本的 token 数不可跨模型直接套用
- 反直觉点：把中文换成英文提示词有时能省 token，但可能损失表达精度，是个真实的取舍

**红旗**：说不出中文和英文的 token 密度差异。

## Q02 · embedding 是什么？相似度为什么用余弦？ <a id="q02"></a>

**考察点**：能不能区分「embedding 相似」和「语义相关」。

**L0 采分点**
- 把文本映射到定长向量，使语义相近的文本在向量空间中距离近
- 余弦相似度只看方向不看模长——文本长度不该影响相似判定，所以用余弦而不是欧氏距离
- 归一化后，余弦相似度和内积等价（这是向量库常用内积的原因）

**L1 采分点**
- embedding 捕捉的是**分布式共现相似**，不等于逻辑相关。经典反例：「订单已取消」和「订单未取消」余弦相似度很高——**这直接导致 RAG 会召回意思相反的文档**
- 所以生产 RAG 里 embedding 只做粗召回，必须配 rerank（cross-encoder）做精排
- 领域词汇（内部产品名、缩写）在通用 embedding 里几乎没有区分度，要么微调 embedding，要么加关键词/BM25 混合检索

**红旗**：只说「把文本变成向量」，说不出它的失效场景。

## Q03 · context window 的本质限制是什么？ <a id="q03"></a>

**考察点**：知不知道「长 context ≠ 长记忆」。

**L0 采分点**
- 是单次前向传播能容纳的 token 上限，由注意力机制的位置编码和显存共同约束
- 注意力的计算/显存开销随序列长度增长（朴素实现是平方级），所以长 context 贵且慢
- **它是每次调用的输入上限，不是记忆**——每次调用都要重新把内容塞进去

**L1 采分点**
- 「lost in the middle」：即使塞得下，模型对中间位置内容的利用率显著低于首尾。所以**关键指令放开头或结尾**
- 长 context 不能替代 RAG 的三个原因：成本线性上涨、注意力被稀释、**没有权限过滤**（RAG 能在检索层做 ACL，全塞进去做不到）
- 长 context 真正适合的是：单份长文档的整体理解、需要全局一致性的改写。不适合：多文档检索、需要权限隔离的场景

**红旗**：说「现在 context 够大了不需要 RAG」。

## Q04 · temperature / top-p / top-k 分别控制什么？生产里怎么设？ <a id="q04"></a>

**考察点**：有没有在生产里调过，还是只知道「调高更有创意」。

**L0 采分点**
- temperature：缩放 logits，改变整个概率分布的陡峭程度。→0 趋近贪心，→1 保持原分布，>1 更平坦
- top-k：只从概率最高的 k 个候选里采样（固定数量）
- top-p（nucleus）：从累计概率达到 p 的最小候选集里采样（**动态数量**，分布陡时候选少、平时候选多）

**L1 采分点**
- 生产默认：**需要确定性/结构化输出的场景 temperature = 0**（工具调用、分类、抽取、JSON 输出）
- 但 **temperature=0 不等于完全确定**：浮点非结合性、batch 组成变化、MoE 路由都会引入抖动。所以「设了 0 就能做回归测试」是错的，评测仍需容忍抖动或跑多次
- top-p 和 temperature 同时调容易互相干扰，通常**只调一个**
- 创意场景调高的代价是幻觉率上升，要用评测量化而不是凭感觉

**红旗**：认为 temperature=0 输出完全可复现。

## Q05 · 从训练目标解释幻觉的成因 <a id="q05"></a>

**考察点**：能不能从机制解释，而不是归因于「数据不够」。

**L0 采分点**
- 预训练目标是**最大化下一 token 的似然**，不是最大化事实正确性。模型学的是「什么样的文本看起来合理」
- 所以在知识边界外，模型会生成**分布上最像正确答案的文本**——流畅、格式正确、但内容编造
- 对齐阶段（RLHF）奖励「有帮助的回答」，进一步惩罚了「我不知道」，**放大**了自信编造的倾向

**L1 采分点**
- 推论一：**幻觉不能靠 prompt 里写「不要编造」根本解决**，只能靠外部证据（RAG）+ 要求引用 + 无依据拒答的策略层
- 推论二：**流畅度和自信度不是正确性的信号**。这正是 Anthropic 那道「模型自信地答错」题的根，见 [Q60](G-安全与上线.md#q60)
- 推论三：模型不知道自己不知道——校准（calibration）在对齐后通常变差，所以不能直接信任模型自报的置信度

**红旗**：答「训练数据里有错误信息」。这是次要原因，不是机制。

## Q06 · 量化牺牲什么换什么？什么场景不能量化？ <a id="q06"></a>

**考察点**：知不知道量化的收益主要在带宽不在算力。

**L0 采分点**
- 把权重（有时还有激活/KV cache）从 FP16 降到 INT8 / INT4 / FP8，牺牲数值精度换显存和带宽
- 收益：显存占用降低（能塞更大模型或更大 batch）、**内存带宽压力降低**——decode 阶段是访存受限的，所以量化对 decode 提速明显
- 代价：精度损失，且**不同任务的敏感度差别很大**

**L1 采分点**
- 敏感度排序（经验）：长链推理、代码生成、数学 > 分类、抽取、改写。所以 **Agent 的规划环节不宜激进量化，工具参数抽取可以**
- KV cache 量化和权重量化是两件事，前者对长 context 场景收益更大
- 不能量化的场景：已经贴着质量红线的高风险任务、需要严格复现的评测基线
- **关键做法**：量化后必须用自己的 golden set 重跑，不能信论文的通用 benchmark 数字

**红旗**：只说「省显存」，说不出对 decode 速度的影响。

## Q07 · 微调 / RAG / 改 prompt，决策依据是什么？ <a id="q07"></a>

**考察点**：面试官最想听到的是「先排除法」，不是「都试试」。

**L0 采分点**
- 判据是**问题的性质**：
  - 缺**知识** → RAG（知识会变、要权限隔离、要可引用）
  - 缺**行为/格式/风格** → 微调（有稳定的输入输出模式、样本充足）
  - 缺**指令清晰度** → 改 prompt / 上下文工程
- 顺序：prompt → RAG → 微调。因为迭代成本和可回滚性依次变差

**L1 采分点**
- 微调**不适合注入易变知识**：模型没法「忘记」，更新要重训，且无法做权限过滤
- 微调的真实成本不在训练，在**数据构造和评测基线**——没有 golden set 就没法判断微调是不是变好了
- 混合是常态：微调让模型学会「怎么用检索结果」和「什么时候拒答」，RAG 提供事实
- 反过来说，如果延迟/成本卡得死，用微调小模型替代大模型 + 长 prompt 是划算的

**红旗**：答「微调效果更好所以优先微调」。

## Q08 · SFT / RLHF / DPO 各解决什么问题？ <a id="q08"></a>

**考察点**：Agent 岗不深挖，但要能说清动机链条。

**L0 采分点**
- **SFT**：用「输入→理想输出」的示范数据做监督微调，教模型**格式和基本行为**。瓶颈是需要人写出理想答案，而很多任务人写不出「最好的那个」
- **RLHF**：人只需**比较两个输出哪个更好**（比写出理想答案容易得多），训一个奖励模型，再用 RL（PPO）优化策略。解决了「示范数据难造」
- **DPO**：跳过显式奖励模型，直接用偏好对做分类式优化。**更简单稳定、成本低**，效果在多数场景接近 RLHF

**L1 采分点**
- 三者是递进解决同一个问题：**如何让模型对齐人的偏好，同时降低数据和训练成本**
- 代价：对齐会带来 alignment tax——泛化能力和校准度可能下降，模型更倾向于给出「听起来好」的答案（接回 [Q05](#q05) 的幻觉机制）
- 对 Agent 岗的意义：你不太会训模型，但要知道**为什么模型倾向于自信、倾向于说「我完成了」**——这是对齐目标的副产物，所以工程上必须以工具事件为真相，见 [Q28](C-Agent边界与工具可靠性.md#q28)

**红旗**：把 DPO 说成「另一种 RL」。它恰恰是绕开了 RL。

## Q09 · KV cache 是什么？为什么它决定推理成本结构？ <a id="q09"></a>

**考察点**：这题能直接区分「用过 API」和「懂推理」。答好了会被追到模块 B。

**L0 采分点**
- 自回归生成时，每生成一个 token 都要对之前所有 token 做注意力。KV cache 把已算过的 key/value 存下来，避免重复计算
- 有了它，decode 阶段每步的**计算量**从随长度增长降为常数级
- 但代价是**显存**：cache 大小 ∝ batch × 序列长度 × 层数 × 头维度，长 context + 大 batch 会直接打爆显存

**L1 采分点**
- 这解释了推理的**两阶段成本结构**（接 [Q13](B-推理与服务基础设施.md#q13)）：
  - **prefill**：一次性处理输入，**算力受限**，可以高度并行
  - **decode**：逐 token，**访存受限**，瓶颈是把 KV cache 和权重从显存搬到计算单元
- 所以「输入 token 便宜、输出 token 贵」不是定价策略，是物理事实
- 工程推论：**KV cache 是 batch size 的真正上限**，不是算力。PagedAttention（vLLM）解决的就是 cache 显存碎片问题
- 对 Agent 的意义：多轮 Agent 循环会不断增长 cache，这是长任务成本爆炸的直接原因（接 [Q36](D-上下文RAG与记忆.md#q36)）

**红旗**：说不出 prefill 和 decode 的瓶颈不同。

## Q10 · structured output 底层怎么实现的？和 prompt 里写「返回 JSON」有什么区别？ <a id="q10"></a>

**考察点**：知不知道有 constrained decoding 这层，还是以为全靠模型听话。

**L0 采分点**
- 两种实现层次：
  1. **prompt 约束**：在提示里描述格式。模型可能不遵守，需要重试和解析容错
  2. **constrained decoding / grammar-based**：在采样时**屏蔽掉会违反 schema 的 token**，从机制上保证输出可解析
- function calling / tool use 一般走第二种，所以结构上是可靠的

**L1 采分点**
- **结构合法 ≠ 内容正确**。constrained decoding 保证 JSON 能解析、枚举值在范围内，但不保证订单号是真的、金额是对的
- 所以**服务端必须重新校验**：类型、范围、权限、业务规则。绝不能因为「schema 约束过了」就直接执行（接 [Q55](G-安全与上线.md#q55)）
- 副作用：强约束会轻微降低模型质量（被限制的路径可能是它想走的），schema 越复杂越明显。设计上应该**拆成多个小 schema 而不是一个巨型嵌套 schema**（接 [Q23](C-Agent边界与工具可靠性.md#q23)）
- 枚举值比自由字符串好——既减少解析失败，也让负向测试可写

**红旗**：认为用了 structured output 就不用服务端校验。
