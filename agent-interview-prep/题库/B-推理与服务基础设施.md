## Q11 · 设计一个推理 batching 系统：单 GPU 一批最多 100 条，用户同步等待 <a id="q11"></a>

> **Anthropic 真题**。这题不是考你会不会写代码，是考你**能不能在延迟和吞吐之间建立可量化的权衡**。

**L0 采分点（先说清核心张力）**
- 核心矛盾：**攒批提高吞吐，但攒批本身增加延迟**。用户同步等待意味着延迟有硬约束
- 所以设计的本质是一个**准入控制 + 排队 + 触发策略**问题，不是模型问题

**L1 采分点（设计要素）**
- **触发条件三选一取先到**：批满 100 / 等待超过 T 毫秒 / 显存达阈值。T 由 SLO 反推，不是拍脑袋
- **必须区分 prefill 和 decode**（接 [Q13](#q13)）：两阶段的 batch 策略不同，prefill 按 token 总数攒批，decode 按序列数
- **continuous batching 而非 static**（接 [Q12](#q12)）：短请求先返回后立刻补位，否则整批被最长的那条拖死
- **队列要分级**：不同 SLO 的流量不能混在一个队列（交互式 vs 批处理），否则长任务饿死短任务
- **过载策略**：队列有上限，超了要**快速拒绝**（返回 429）而不是无限排队——排到用户超时的请求是纯浪费

**L2 采分点（失败模式）**
- **队头阻塞**：一条超长输入把整批 prefill 拖住，所有人 TTFT 飙升 → 按 token 数而非请求数限批
- **显存 OOM**：batch 攒够了但 KV cache 放不下（接 [Q09](A-LLM基本功.md#q09)）→ 准入时要按**预估 cache 占用**而非请求数判断
- **尾延迟塌方**：平均延迟正常但 p99 极差，因为长请求全堆在一起 → 按长度分桶
- **重试风暴**：超时的客户端重试，加剧过载 → 需要背压和幂等

**L3 采分点（怎么验证）**
- 指标必须分开看：**TTFT、ITL、端到端 p50/p95/p99、GPU 利用率、吞吐（tok/s）、拒绝率**
- 压测要有**混合负载**（长短请求按真实分布混合），只用等长请求压测会得出虚高结论
- 用「饱和点」验证：逐步加压直到 p95 突破 SLO，那个 QPS 才是真实容量，不是 GPU 打满时的 QPS

**红旗**：全程只谈 batch size，不谈延迟 SLO 和显存约束。

## Q12 · static batching 与 continuous batching 的差别？为什么后者对 LLM 更重要？ <a id="q12"></a>

**L0 采分点**
- **static**：凑齐一批一起进、一起出。批内所有请求必须等最慢的那条完成
- **continuous（in-flight）**：以**迭代**为单位调度。某条序列生成完就立刻退出、空位立刻补新请求进来

**L1 采分点**
- 为什么对 LLM 特别重要：**输出长度差异巨大且事先不可知**。一条生成 20 token、一条生成 2000 token，static 下前者要陪跑 100 倍时间
- 收益量级：真实混合负载下吞吐提升常在数倍，GPU 利用率从 30–40% 提到 80%+
- 代价：调度复杂度、需要 PagedAttention 一类的显存管理来支持动态增删序列
- 这是 vLLM / TensorRT-LLM 一类框架的核心价值，**面试时要说得出它替你解决了什么**，不能只报框架名

**红旗**：说得出两个名词的定义，说不出「输出长度不可知」这个根本原因。

## Q13 · prefill 与 decode 的资源特征有什么不同？为什么要分离？ <a id="q13"></a>

**L0 采分点**

| | prefill | decode |
| --- | --- | --- |
| 处理 | 一次性处理全部输入 | 逐 token 生成 |
| 瓶颈 | **算力受限**（compute-bound） | **访存受限**（memory-bound） |
| 并行度 | 高，可大批 | 低，每步只算一个 token |
| 影响指标 | TTFT | ITL |

**L1 采分点**
- 混在一起调度的问题：**一个大 prefill 会打断正在进行的 decode**，导致已经开始输出的用户卡顿（ITL 抖动）
- 分离部署（disaggregated serving）把两阶段放不同实例，各自用最优的批策略和硬件配置。代价是要跨节点传 KV cache，需要高速互联
- 折中方案 **chunked prefill**：把长 prefill 切片，穿插在 decode 之间，用少量 TTFT 换 ITL 平稳
- 决策依据：**交互式产品优先保 ITL 平稳**（用户对卡顿敏感），批处理场景优先保吞吐

**红旗**：说不出「访存受限」这个词背后的含义——decode 每步都要把整个 KV cache 和权重过一遍显存带宽。

## Q14 · TTFT 和 ITL 分别被什么决定？怎么分别优化？ <a id="q14"></a>

**L0 采分点**
- **TTFT**（time to first token）= 排队时间 + prefill 时间。由输入长度、队列深度、prefill 批策略决定
- **ITL**（inter-token latency）= 每步 decode 时间。由模型大小、显存带宽、当前 batch 大小决定
- 端到端延迟 = TTFT + ITL × 输出长度

**L1 采分点**
- 优化 TTFT：**prompt caching**（接 [Q17](#q17)）、缩短输入、限制队列深度、chunked prefill、预热
- 优化 ITL：量化（降带宽压力）、投机解码（speculative decoding）、减小 batch、更小的模型
- **优化输出长度往往收益最大且最容易被忽略**：让模型少说废话、用结构化输出替代自然语言，端到端延迟直接线性下降
- 两者会互相拉扯：加大 batch 提吞吐但抬高 ITL。**必须先定 SLO 再优化**，否则会在两个指标之间反复横跳

**L2 采分点（Agent 场景特有）**
- Agent 是**多轮串行调用**，端到端延迟 = Σ 每轮延迟。一轮 2 秒，5 轮就是 10 秒
- 所以 Agent 的延迟优化重点是**减少轮数**（更好的工具设计、并行工具调用），而不是单轮提速
- 流式输出能极大改善**感知延迟**，但对需要等工具结果才能说话的 Agent 用处有限——这时候要给中间状态反馈（「正在查询订单…」）

**红旗**：只说「优化延迟」，不区分 TTFT 和 ITL。

## Q15 · 吞吐与延迟怎么权衡？SLO 怎么定？ <a id="q15"></a>

**L0 采分点**
- 二者本质冲突：提吞吐靠攒批和高并发，两者都抬高单请求延迟
- 所以正确顺序是**先定延迟 SLO（约束），再在约束下最大化吞吐（目标）**——反过来做一定失控

**L1 采分点**
- SLO 要**分档定**，不是一个数：
  - 交互式对话：TTFT p95 < 1s，ITL p95 < 50ms
  - Agent 后台任务：端到端 p95 < 30s，TTFT 不敏感
  - 批处理：无延迟 SLO，只要吞吐和成本
- 用 **p95/p99 而不是平均**。平均值会被大量快速请求拉低，掩盖尾部体验
- 定 SLO 的依据是**用户行为数据**（超过多久用户会流失/重试），不是技术能力
- 容量规划看**饱和点**：p95 突破 SLO 时的 QPS，而不是 GPU 利用率 100% 时的 QPS

**红旗**：给一个统一 SLO 覆盖所有流量类型。

## Q16 · 设计一个 GPU 配额 / credit 管理系统 <a id="q16"></a>

> **OpenAI 真题**。考的是分布式限流 + 计费 + 公平性，不是 GPU 本身。

**L0 采分点**
- 三件事要分开：**配额（能用多少）、限流（多快能用）、计费（用了多少）**。很多人把三者混为一谈
- 计量单位不能用「请求数」——LLM 请求成本差异极大。要用 **token**，且 **input/output 分别计价**（成本结构不同，接 [Q09](A-LLM基本功.md#q09)）

**L1 采分点**
- **预扣 + 结算**两阶段：请求前按 max_tokens 预扣，完成后按实际用量结算并退还差额。否则无法防止「一个请求打爆配额」
- 限流用 **token bucket**，且要**双维度**：RPM（请求数）和 TPM（token 数）都要限，只限一个都会被绕过
- 分布式一致性：多副本下计数要么用 Redis 原子操作，要么**本地限流 + 全局异步校正**（容忍少量超发，换低延迟）
- 公平性：多租户下需要防止单租户饿死其他人 → 每租户独立桶 + 全局桶双层
- 超限行为：返回 **429 + Retry-After**，让客户端能正确退避。直接丢弃会引发重试风暴

**L2 采分点**
- **流式请求的计费时点**：连接中断时已生成的 token 要不要计费？不处理会被刷
- **预扣过度**：用户都填 max_tokens=4096 但实际只用 200，配额被虚占 → 需要按历史实际用量做动态预扣
- **时钟漂移**导致多副本限流窗口不对齐，出现瞬时超发

**L3 采分点**
- 验证：并发压测下总用量不超配额（正确性）、单租户超限不影响其他租户（隔离性）、限流延迟增加 < 5ms（性能）
- 对账：计费数据与实际推理日志按天对账，偏差 > 0.1% 要告警

**红旗**：用请求数做配额单位。

## Q17 · prompt caching 怎么生效？设计 prompt 时怎么配合它？ <a id="q17"></a>

**考察点**：这题对 Agent 岗**成本控制**极其实用，答好了很加分。

**L0 采分点**
- 缓存的是 **prefill 阶段算出的 KV cache**，命中后跳过这部分重算，直接降 TTFT 和输入成本
- 命中条件是**前缀完全匹配**——从第一个 token 开始逐 token 一致，一旦某处不同，后面全部失效；匹配通常按块进行，且有最小可缓存长度

**L1 采分点**
- 设计推论（这是采分重点）：**把 prompt 按变化频率从低到高排列**
  ```
  [系统指令] [工具定义] [长期知识/few-shot] | [会话历史] | [本轮输入]
   ←──────── 稳定，可缓存 ────────────→   ←── 变化 ──→
  ```
- 常见错误：把**时间戳、随机 ID、用户名**放在 prompt 开头 → 缓存永远不命中
- 工具定义放在前面而不是穿插在中间；工具集频繁变动会击穿缓存，这是「工具集要稳定」的一个额外理由（接 [Q24](C-Agent边界与工具可靠性.md#q24)）
- 缓存有 TTL，低频调用命中率低；缓存写入本身可能有额外成本，要算净收益
- **Agent 场景收益最大**：多轮循环里系统指令和工具定义每轮都重复，缓存能省掉大部分输入成本

**L2 采分点**
- 命中率上不去的排查顺序：前缀里有无变量 → 工具定义是否被动态排序（**dict 序列化顺序不稳定是经典坑**）→ 是否超过 TTL → 是否达到最小可缓存长度
- 缓存命中率是个必须上 dashboard 的指标，否则成本悄悄涨了都不知道

**红旗**：说不出「前缀完全匹配」这个约束，或者说不出该把什么放前面。

## Q18 · 一次 Agent 请求的成本由哪些部分构成？怎么定位大头？ <a id="q18"></a>

**L0 采分点**
- 成本 = Σ（每轮 input token × 单价 + 每轮 output token × 单价）+ 工具调用成本 + 检索成本 + 重试成本
- **关键认知：Agent 的成本随轮数近似平方增长**——每轮都要把之前的全部历史再传一遍作为 input
- 追问「开了 prompt caching 还是平方吗」：**仍是平方，但系数降到十分之一量级**（重复前缀走缓存读）。缓存改变斜率不改变形状，轮数多了压缩历史仍躲不掉
- 所以「减少轮数」比「换便宜模型」通常收益更大

**L1 采分点**
- 定位大头的顺序：
  1. 先看**轮数分布**（p50/p95 轮数），长尾任务往往贡献大部分成本
  2. 再看**单轮 input token 构成**：系统指令 / 工具定义 / 历史 / 检索结果，哪块最胖
  3. 再看**重试和失败**：失败任务的成本是纯损失，failed task 的成本占比是个高信号指标
- 正确的成本指标是 **cost per successful task**，不是 cost per call。后者会奖励「早早失败」
- 优化手段按性价比排序：prompt caching → 压缩历史/摘要 → 缩小工具集 → 模型分级路由 → 并行工具调用 → 换模型

**L2 采分点**
- 成本失控最常见的三个原因：**循环没有预算上限**、**检索结果全量塞进 context**、**失败后无限重试**
- 检索结果是最容易被忽略的大头：top-k 从 5 改到 20，成本涨 4 倍但质量常常不变

**L3 采分点**
- trace 里必须记：每轮的 input/output token、缓存命中、工具耗时、总轮数、终止原因
- dashboard 要按**任务类型分段**看成本，平均值会把「大量廉价简单任务」和「少量昂贵复杂任务」混在一起（接 [Q52](F-评测可观测与排错.md#q52)）

**红旗**：只说「token 贵」，说不出轮数的平方效应。
