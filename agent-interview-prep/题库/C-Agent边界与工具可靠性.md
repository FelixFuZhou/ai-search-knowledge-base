# 模块 C：Agent 边界、工具与可靠性（Q19–Q28）

> **定位**：Agent 岗的地基。这 10 题的 L2 **全部**能从[主线项目](../主线项目/README.md)产出，是投入产出比最高的一块。
>
> 判断标准：如果你的 L2 里没有具体数字和「我当时先怀疑 X，结果是 Y」，说明主线项目还没做到位。

## Q19 · 什么是 Agent？与单次 LLM 调用、与 workflow 的边界在哪？ <a id="q19"></a>

**考察点**：能不能划出**三分**边界。只答「Agent 会调工具」是本科生答案。

**L0 采分点**
- 三者的区分点是**控制流由谁决定**：
  - **单次调用**：无控制流
  - **workflow**：控制流**写死在代码里**，模型只填空
  - **Agent**：控制流**由模型在运行时决定**——下一步做什么、还要不要继续，是模型的输出
- 所以 Agent 的定义性特征是「模型进入了控制流」，不是「有工具」也不是「多轮」

**L1 采分点**
- 由此推出取舍：**模型进入控制流 = 换来适应性，付出可预测性**。步骤事先可枚举就用 workflow，不可枚举才用 Agent
- 多轮聊天不是 Agent（没有环境反馈和目标状态）；固定的「检索→生成」也不是 Agent（控制流写死了）
- 混合是常态且往往最优：**外层确定性状态机 + 内层单步 Agent 做受约束选择**。这是我主线项目的架构

**L2 采分点**
- 常见误判：把「if-else 太多不好维护」当成上 Agent 的理由。结果是不可预测性替代了可读性，问题更难查
- 反向误判：需求确实开放（用户意图无法枚举）却硬写 workflow，结果是分支爆炸

**L3 采分点**
- 验证「该不该用 Agent」的实际做法：先用 workflow 实现，统计**兜底分支的触发率**。低于某个阈值说明 workflow 够用

**红旗**：第一句是「Agent 是一种能自主完成任务的智能体」。

## Q20 · 哪些需求不该用 Agent？ <a id="q20"></a>

**L0 采分点**
- 四类不该用：
  1. **步骤固定且可枚举** → 代码/workflow 更快更便宜更可测
  2. **容错率极低**（支付、医疗、法律出具） → 不可预测性的代价太高
  3. **延迟/成本敏感** → Agent 的多轮循环成本随轮数快速增长（接 [Q18](B-推理与服务基础设施.md#q18)）
  4. **需要严格可复现**（审计、合规） → 模型输出天然有抖动

**L1 采分点**
- 判断句式：**「这个需求的分支能不能事先枚举完？」**能就不用 Agent
- 真实场景往往是**部分该用**：意图识别和参数澄清用模型（开放），执行流程用代码（固定）。把「用不用 Agent」当成二选一是新手标志
- 反过来，Agent 真正不可替代的场景只有一个特征：**下一步依赖上一步的结果，且依赖关系事先不知道**

**红旗**：答不出「先用确定性方案试试」这个默认立场。

## Q21 · 一个生产 Agent 的最小组件有哪些？ <a id="q21"></a>

**L0 采分点**（八层，能顺下来即可）

```
model        选型、版本固定、降级路线
instructions 系统指令，版本化管理
state        会话状态 + 任务状态，可持久化
tools        schema + 实现 + 权限
policy       预算、审批、允许/禁止的动作
runtime      循环控制、超时、重试、并发
observability trace / 指标 / 日志
eval         golden set + 评分器 + 回归门禁
```

**L1 采分点**
- **Demo 和生产的差别不在前四层，在后四层**。Demo 缺的是 policy / observability / eval
- 最容易被漏掉的是 **policy 层**：很多人把预算和权限写进 prompt。prompt 是建议，policy 必须在**执行层**强制（接 [Q54](G-安全与上线.md#q54)）
- **state 要区分两种**：会话状态（可丢，重建即可）和任务状态（不可丢，涉及副作用）。混在一起会导致重启后重复执行

**L2 采分点**
- 我在主线项目里最先补的是 trace，因为**没有 trace 的时候所有排错都是猜**。第一版没有 trace，一个「订单取消失败」查了两小时，加了 trace 后同类问题 5 分钟定位
- 第二个补的是 policy 层——最初把「金额 > 500 需审批」写在 prompt 里，注入测试直接绕过

**红旗**：只答「模型 + 工具 + 循环」。

## Q22 · 如何定义任务的成功、失败与停止？ <a id="q22"></a>

**L0 采分点**
- **成功**必须是**可被后端验证的状态**，不是模型的自我声明（接 [Q28](#q28)）
- **停止条件**至少四类：达成目标 / 超预算（步数、token、时间、金额）/ 不可恢复错误 / 需要人介入
- **失败要分类**，不能只有一个 `failed`：参数不足、无权限、工具失败、无资格、用户放弃

**L1 采分点**
- 为什么失败要分类：不同失败对应**不同的下一步动作**（澄清 / 拒绝 / 重试 / 转人工）和**不同的告警级别**。一个笼统的 failed 让线上完全无法运营
- 每个终止状态都要有**明确的用户可见结果**——「静默停止」是最差的失败模式，用户不知道发生了什么
- 预算要**多维度同时限**：只限步数，模型会在单步里塞进巨大的 context；只限 token，会无限循环小步骤

**L2 采分点**
- 主线项目里遇到的：只设了 max_steps=10，结果工具连续超时时，10 步全耗在重试上，用户等了 40 秒得到一个「失败」。修复是加了**总时长预算 15s**，并且**重试不计入 step 但计入时长**
- 另一个：模型在「无资格退款」时不停尝试其他工具找变通路径，因为终止条件里没有「业务规则拒绝」这个合法终态

**L3 采分点**
- 每个终止状态都要有对应的 eval case，尤其是**拒绝**和**转人工**——这两类最容易在优化过程中被误伤（模型变得更「乐于助人」，该拒的不拒了）

**红旗**：只说「设置最大步数」。

## Q23 · 好的工具 schema 怎么设计？ <a id="q23"></a>

**L0 采分点**
- 六条：**单一职责**、名称/描述让模型能区分、**强类型 + 枚举优先于自由字符串**、入参尽量少、**结构化错误返回**、幂等标识
- 描述写给模型看的重点是**什么时候该用、什么时候不该用**，而不是这个函数干什么

**L1 采分点**
- 为什么要拆分而不是一个大工具：`manage_order(action="cancel"|"query"|"refund")` 这种设计让模型的选择空间变成了参数空间，**无法做工具级权限控制**，也无法写「不应调用」的负向测试
- 描述里加**反例**收益极大：`get_order` 的描述写「当用户询问订单状态时使用；**当用户想取消订单时不要用这个，用 cancel_order**」
- 错误返回要结构化：`{code, message, retryable, user_message}`。`retryable` 让 runtime 能判断，`user_message` 保证不泄露内部信息（接 [Q27](#q27)）
- 工具定义会占 prompt 且影响缓存（接 [Q17](B-推理与服务基础设施.md#q17)），**工具集要稳定且精简**

**L2 采分点**
- 主线项目里，最初 `cancel_order(order_id, reason)` 的 `reason` 是自由字符串，模型编出各种理由导致下游统计混乱。改成枚举后问题消失，**且模型的工具选择准确率也上升了**——枚举缩小了它的想象空间

**L3 采分点**
- 每个工具至少三条测试：正确调用、**参数不全时不调用**、**不该调用时不调用**。第三条最常被漏（接 [Q24](#q24)）

**红旗**：设计一个 `execute_action(action, params)` 的万能工具。

## Q24 · 如何防止模型调用错误的工具？ <a id="q24"></a>

**L0 采分点**
- 五层防御，从上到下：
  1. **精简工具集**——最有效的一招。工具数量和选择准确率负相关
  2. **描述区分度**——尤其是相似工具，描述里显式写「不要用这个的场景」
  3. **工具路由/分组**——按意图先分组，只暴露相关子集
  4. **allowlist**——按角色/阶段限制可用工具，在**执行层**拦截
  5. **负向测试**——每个工具都有「不应被调用」的用例

**L1 采分点**
- 前三层降低概率，**后两层保证安全**。只做前三层是不够的——概率再低乘以流量也是事故
- 工具数量的经验阈值：超过 10–15 个准确率明显下降。超了就要分组或改成两阶段（先选组再选工具）
- **澄清优于猜测**：模型不确定时应该问，而不是选一个最像的。这要在系统指令里显式要求，并在 eval 里奖励

**L2 采分点**
- 主线项目：`get_order` 和 `get_order_history` 长期混用，因为描述都是「查询订单信息」。改成「`get_order`：按订单号查**单个**订单当前状态」和「`get_order_history`：查某用户**最近的多个**订单，**已知订单号时不要用**」后，混用率从约 18% 降到 2%

**L3 采分点**
- 评测要**分开测工具选择和最终回答**——回答对了但工具选错，会被最终答案的评分掩盖（接 [Q45](F-评测可观测与排错.md#q45)）

**红旗**：只答「把 prompt 写清楚」。

## Q25 · 用户参数不全时怎么办？ <a id="q25"></a>

**L0 采分点**
- 原则：**调用前收集齐必填参数，缺就问，不猜**
- schema 里明确 required / optional；模糊值（「上周那个订单」）要**回显候选让用户确认**，不能自己选一个
- 澄清要**一次问全**，不要挤牙膏式一轮问一个

**L1 采分点**
- 危险的不是「没问」，是**猜了还猜对了大部分时候**——这会让问题在测试中隐形，在长尾中爆发
- 什么时候可以不问：能从上下文**唯一确定**时。「唯一」是关键，有两个候选就必须问
- 澄清次数也要有预算，无限澄清等于死循环。通常 2 次问不清就转人工

**L2 采分点**
- 主线项目里最贵的一个 bug：用户说「取消我的订单」，只有一个进行中订单时模型直接取消了——看起来合理。但用户其实指的是**另一个已完成订单**想退货。修复是**永远先回显订单详情让用户确认**，即使只有一个候选。这条规则让澄清轮次上升了，但错误取消率归零

**L3 采分点**
- eval case 必须包含：无参数、参数模糊、**有多个相似候选**（最容易出错）、参数明确
- 「有多个相似候选时是否询问」应该是一条独立的评分项

**红旗**：答「用默认值」。

## Q26 · 工具有副作用，如何避免重复执行？ <a id="q26"></a>

**L0 采分点**
- 四件事：**幂等键**（业务维度构造，如 `order_id + action + request_id`）、**执行前查状态**、**明确用户确认**、**失败分类决定要不要重试**
- 幂等的保证点在**服务端**，不在 Agent。Agent 只负责传一致的幂等键

**L1 采分点**
- 重试的两难：网络超时时你不知道对方执行没执行。**只有幂等能解决**，重试策略不能解决
- 幂等键必须**在第一次调用前生成并持久化**，重试时复用。如果每次重试都生成新键，等于没有幂等
- 区分可重试和不可重试：超时/5xx/限流 → 可重试；4xx/业务规则拒绝 → 不可重试，重试只会浪费预算
- 不可幂等的外部系统要用 **Saga/补偿**（接 [Q58](G-安全与上线.md#q58)）

**L2 采分点**
- 主线项目里的实际事故：`submit_refund` 超时后 runtime 自动重试，产生了两笔退款。当时的幂等键用的是 `order_id + timestamp`——**timestamp 每次重试都变**，等于没有幂等。改成任务创建时生成一次 `request_id` 并存进任务状态后解决
- 更隐蔽的一个：Agent 循环重启后从头开始，之前的副作用已经发生。修复是**恢复时先查后端真实状态**而不是重放（接 [Q58](G-安全与上线.md#q58)）

**L3 采分点**
- 负向测试：**同一请求连发两次，断言只产生一次副作用**。这条测试必须进 CI
- 更强的：在工具调用后注入超时，验证重试后仍只有一次副作用

**红旗**：只说「加幂等键」，说不出键怎么构造、什么时候生成。

## Q27 · 工具超时或返回 500 怎么处理？如何避免无限循环？ <a id="q27"></a>

**L0 采分点**
- 工具错误要**结构化返回给模型**，让它能做出正确决策，而不是抛异常或返回原始堆栈
- 返回给模型的错误里**绝不能有**：堆栈、内部主机名、SQL、密钥、其他用户数据
- 循环控制：step / token / 时长 / 金额多维预算 + **重复调用检测**（同工具同参数连续 N 次）+ 明确的 abort 终态

**L1 采分点**
- 错误信息给模型看的应该是**可行动的**：「订单服务暂时不可用，可稍后重试」比「HTTP 500」有用得多。前者模型知道该告诉用户等待，后者模型可能去尝试别的工具
- 退避策略：指数退避 + 抖动。**抖动很重要**，否则多个失败请求会同步重试形成尖峰
- 部分成功要显式建模：三个工具调用成功两个，状态不是「失败」而是「部分完成」，恢复时只补没做的
- **循环检测比预算更早生效**：模型卡在同一个失败工具上时，10 步预算会全耗掉，检测到连续 3 次相同调用就该跳出

**L2 采分点**
- 主线项目：工具超时后模型会「换个说法再试一次」——参数微调但语义相同，所以**参数精确匹配的循环检测失效**。改成对参数做归一化后再比较（去掉自由文本字段）才检测到
- 另一个坑：超时的工具其实执行成功了，只是响应慢。模型收到「失败」后告诉用户失败，用户看到的却是操作已完成。修复是超时后**查状态而非假设失败**

**L3 采分点**
- 测试：模拟 timeout、500、429，断言 ①不泄露内部信息 ②有用户可见的说明 ③不无限重试 ④最终进入明确终态
- 人为让工具连续失败，断言 Agent 在预算内停止并给出可理解的结论

**红旗**：把原始异常信息直接塞回给模型。

## Q28 · 模型说「已完成」但并没有调用工具，怎么避免？ <a id="q28"></a>

> 这题是 Agent 岗的**试金石**。它把 [Q05](A-LLM基本功.md#q05)（对齐让模型倾向说好听的）和 [Q45](F-评测可观测与排错.md#q45)（不能只看回答）串起来了。

**L0 采分点**
- 根本原则：**真相来源是工具事件和后端状态，不是模型的话**
- 实现上：面向用户的成功回复必须由**已验证的工具结果**渲染，而不是由模型自由生成
- 成因不是 bug，是对齐的副产物——模型被训练成倾向于给出「有帮助的、完成态的」回答（接 [Q08](A-LLM基本功.md#q08)）

**L1 采分点**
- 三层防护：
  1. **架构层**：终态回复由代码根据工具返回值组装，模型只负责措辞
  2. **校验层**：声称成功时检查本轮是否有对应的成功工具事件，没有就拦截并重试/转人工
  3. **评测层**：轨迹评测（trajectory eval）——断言「工具 X 被调用且成功」，而不只是断言回答里有「已取消」
- 让模型完全自由生成终态回复，在有副作用的场景是**架构缺陷**，不是 prompt 问题

**L2 采分点**
- 主线项目里这个问题出现在**工具超时之后**：模型收到超时错误，但仍然回复「您的订单已成功取消」。因为它把「用户想取消」和「流程走完了」混为一谈
- 更隐蔽的变体：工具调用**成功了但返回的是「无资格退款」**，模型仍然说「退款已提交」——它把工具调用成功当成了业务成功。所以校验要看的是**业务结果字段**，不是 HTTP 状态

**L3 采分点**
- 必写一条测试：**回答文本正确但工具未调用 → 必须判为 fail**。这条 case 是检验你的评测体系有没有轨迹维度的最快方法
- 线上监控：「声称成功」与「后端实际成功」的差值，这个指标为 0 才算真的解决

**红旗**：答「在 prompt 里强调必须调用工具」。
