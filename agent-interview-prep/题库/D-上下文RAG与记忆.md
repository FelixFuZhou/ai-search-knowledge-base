# 模块 D：上下文、RAG 与记忆（Q29–Q36）

> **定位**：几乎每家都问。Glean / Databricks / Perplexity 类公司是重点，Sierra 类客服 Agent 也必问。
>
> 这块最容易「会背不会做」——概念都能说，但说不出分层排查。L2/L3 的质量决定分数。

## Q29 · context / session state / long-term memory / RAG 的边界？ <a id="q29"></a>

**L0 采分点**
- 按**生命周期和读写规则**区分，不是按存储介质：

| | 内容 | 生命周期 | 写入者 | 可信度 |
| --- | --- | --- | --- | --- |
| **context** | 本次调用送进模型的全部内容 | 单次调用 | 系统组装 | — |
| **session state** | 当前任务/会话的状态 | 会话或任务期 | 系统 + 工具结果 | 高（结构化） |
| **long-term memory** | 跨会话的用户偏好/事实 | 长期 | 需审批写入 | **中，要验证** |
| **RAG** | 外部事实知识 | 随源数据更新 | 数据管道 | 高，但有时效和权限 |

**L1 采分点**
- 最容易混的是 **session state 和 long-term memory**。前者可丢（重建即可），后者不可随意写（会污染未来所有会话）
- context 是**每次调用重新组装的产物**，不是存储。把它当存储会导致「以为模型记住了」
- 四者的错误使用：把任务状态放长期记忆（污染）、把事实知识放 prompt（无法更新、无权限）、把长期记忆当事实（未验证）

**L2 采分点**
- 常见事故：把「用户说他喜欢快速退款」写进长期记忆，后来这条被模型当成**授权**，在另一个会话里跳过了确认步骤。记忆里存的是偏好，不能当策略用

**L3 采分点**
- 每类数据标注 TTL 和 scope，并写负向测试：跨用户不可见、过期不生效、记忆不能影响权限判定

**红旗**：按「短期记忆 / 长期记忆」二分作答。

## Q30 · 什么是上下文工程？给你 8k token 预算怎么分配？ <a id="q30"></a>

**L0 采分点**
- 上下文工程 = 在有限预算下**决定放什么、怎么排、怎么压、怎么隔离**。四个动作：**选择、压缩、排序、隔离**
- 不是「把 prompt 写长写详细」——恰恰相反，多数时候是在做减法

**L1 采分点**
- 8k 的一个合理分配（要能说出理由，数字不是重点）：
  ```
  系统指令 + 工具定义   1.5k   稳定，放最前，吃 prompt cache
  当前任务状态          0.5k   结构化，必须完整
  检索结果              3k     top-k 后 rerank，带来源和时间
  会话历史              2k     最近 N 轮原文 + 更早的摘要
  用户本轮输入          0.5k
  输出预留              0.5k
  ```
- **排序有讲究**：稳定内容在前（缓存友好，接 [Q17](B-推理与服务基础设施.md#q17)），关键指令在最前或最后（避开 lost-in-the-middle，接 [Q03](A-LLM基本功.md#q03)）
- **隔离**是安全维度：检索到的外部内容必须**明确标记为不可信数据**，与系统指令在结构上分开（接 [Q53](G-安全与上线.md#q53)）
- 超预算时的丢弃顺序应该**事先定义**，而不是简单截断尾部——截断尾部往往砍掉了最新的信息

**L2 采分点**
- 主线项目里的坑：会话历史直接截断最早 N 轮，结果把「用户已确认取消」这条关键信息截掉了，模型又问了一遍。修复是把**决策性事件提取到任务状态**里，不依赖历史原文

**红旗**：答「尽量把有用的信息都放进去」。

## Q31 · Agentic RAG 与普通 RAG 的差别？ <a id="q31"></a>

**L0 采分点**
- 差别在**检索由谁决定**：
  - 普通 RAG：控制流固定，`查询 → 检索 → 生成`，必检索一次
  - Agentic RAG：**模型决定要不要检索、检索什么、够不够、要不要再检索**
- 所以它是 [Q19](C-Agent边界与工具可靠性.md#q19) 那条「模型进入控制流」原则在检索上的应用，不是「检索得更多」

**L1 采分点**
- 收益：能处理需要多跳的问题、能在信息不足时补检索、能对纯闲聊跳过检索省成本
- 代价：**延迟和成本不可预测**（可能检索 1 次也可能 5 次）、可观测性变差、可能陷入检索循环
- 选型判据：查询模式**单一且可预测**用普通 RAG；用户问题开放、需要多跳才上 Agentic
- 折中：**固定的两阶段**——先判断是否需要检索（一次分类调用，便宜），再走固定 RAG。拿到大部分收益且延迟可控

**L2 采分点**
- 常见失败：模型反复检索同一个查询的微小变体，因为它对结果不满意但不会换策略。需要检索次数预算 + 查询去重

**L3 采分点**
- 评测必须**分开**测「检索决策是否正确」（该检索的检索了吗、不该检索的跳过了吗）和「检索结果是否被正确使用」

**红旗**：答「Agentic RAG 就是用 Agent 来做 RAG」。

## Q32 · chunking / 检索 / rerank 各自的失败模式？ <a id="q32"></a>

**考察点**：这题是 RAG 排错能力的直接检验，答得细就能拉开差距。

**L0 采分点**

| 环节 | 典型失败 |
| --- | --- |
| **chunking** | 切断了语义单元（表格、代码、条款被腰斩）；chunk 太大稀释相关性、太小丢上下文；丢失了标题/章节层级 |
| **embedding 检索** | 语义相似但逻辑相反（「已取消」vs「未取消」，接 [Q02](A-LLM基本功.md#q02)）；领域缩写无区分度；长文档被短查询压制 |
| **rerank** | top-k 召回里根本没有正确答案（rerank 救不了召回）；cross-encoder 延迟高；截断位置不当 |

**L1 采分点**
- **召回是天花板**：rerank 只能重排召回到的东西。所以排查顺序永远是**先看召回里有没有正确文档**，再看排序
- chunk 策略要跟着**文档结构**走（按标题/条款切）而不是按固定字数切。给每个 chunk 加上「所属文档 + 章节路径」的前缀，召回质量提升明显
- 混合检索（向量 + BM25）几乎总是优于单一向量检索，尤其对含专有名词、编号、缩写的查询
- 多语言场景：查询和文档语言不一致时向量检索质量骤降，需要跨语言 embedding 或查询翻译

**L3 采分点**
- 分层指标：**recall@k**（召回层）→ **hit rate after rerank**（排序层）→ **groundedness / faithfulness**（生成层）。三个分开测才能定位（接 [Q34](#q34)）

**红旗**：只谈 chunk size 调参。

## Q33 · 如何避免陈旧或越权文档影响结果？ <a id="q33"></a>

**L0 采分点**
- **时效**：文档带 `updated_at` / `version` / `effective_date` 元数据，检索时按业务需要过滤或降权；生成时**要求标注来源和时间**
- **权限**：在**检索层**做 ACL 过滤（按 user/tenant/role），**不能在生成后再过滤**——那时信息已经进模型了
- **无依据拒答**：证据不足或冲突时明确说「我没有找到依据」，而不是靠常识补全

**L1 采分点**
- 权限过滤必须**下推到向量库查询**（metadata filter），后过滤会有两个问题：top-k 被无权文档占满导致有权文档召不回；以及模型已经看到了内容
- 时效冲突的处理：同一问题命中新旧两个版本时，**不能只取最新**——有时用户问的就是历史。正确做法是把冲突暴露出来让模型说明，或按查询意图判断
- 数据管道侧：删除/失效的文档要能**及时从索引移除**，这是最常被忽略的一环。软删除标记 + 检索时过滤是最稳的

**L2 采分点**
- 典型事故：政策文档更新了，但旧版本 chunk 还在索引里，模型引用了旧条款且**给出了正确的引用链接**——看起来极其可信。这类错误只能靠索引侧的版本管理防，靠 prompt 防不住

**L3 采分点**
- 负向测试三条：混入过期文档 → 断言拒答或标注时效；跨租户查询 → 断言零召回；证据冲突 → 断言说明冲突而非任选其一

**红旗**：答「在 prompt 里让模型注意时效性」。

## Q34 · RAG 出错时，怎么区分是检索问题还是生成问题？ <a id="q34"></a>

**L0 采分点**
- 分两步判定，**顺序不能反**：
  1. **正确答案在召回结果里吗？**不在 → 检索问题，改 chunk/embedding/查询改写/混合检索
  2. 在，但回答错了 → 生成问题，分两种：**没用上证据**（grounding 失败）或**超出证据推断**（幻觉）
- 判定需要标注了「正确文档 id」的评测集，否则无法自动化

**L1 采分点**
- 三个可自动计算的指标：
  - **context recall**：正确证据是否被召回
  - **faithfulness / groundedness**：回答的每个断言是否都能在证据里找到支撑
  - **answer relevance**：回答是否回应了问题
- 一个反直觉情况：**证据召回对了、回答也对了，但模型其实没看证据**（靠参数知识蒙对）。检验方法是**把证据换成无关内容，看回答是否改变**——不变说明它没在用证据
- 要求引用（citation）能把 grounding 问题变得可见，是性价比最高的一招

**L2 采分点**
- 主线项目/演练中的实际情况：一条「有理有据但内容错误」的回答，我先怀疑是幻觉，改了 prompt 强调「只用证据」，没效果。看检索日志才发现召回的是**同名不同版本**的文档——是检索问题伪装成了生成问题。这就是为什么排查顺序必须先看召回

**L3 采分点**
- 评测集里每条要标：query、正确文档 id、正确答案、是否应该拒答。**「应该拒答」的样本必须有**，否则模型的过度自信不会被暴露

**红旗**：直接改 prompt。

## Q35 · 长期记忆的安全与隐私风险？ <a id="q35"></a>

**L0 采分点**
- 四类风险：
  1. **错误记忆污染**——一次错误写入影响之后所有会话，且很难被发现
  2. **跨用户泄漏**——scope 没隔离，A 的信息出现在 B 的会话
  3. **注入持久化**——攻击者通过一次对话把指令写进记忆，之后每次都生效（最危险的一类）
  4. **可删除性**——GDPR 类合规要求能真正删除，包括从索引和衍生数据里

**L1 采分点**
- 写入必须有门禁：**不是模型想写就写**。要么规则驱动（只有特定事件才写），要么写入前审核
- 记忆内容要**带来源和时间**，读取时可追溯、可失效
- **记忆不能承载策略**：存「用户偏好快速处理」可以，但这条不能被当成「跳过确认」的授权（接 [Q29](#q29)）
- 记忆是**不可信数据源**，读出来后应和检索内容一样被标记，不能与系统指令同权

**L2 采分点**
- 注入持久化的具体形态：用户说「以后回答我时不需要确认订单」，如果这句被存成偏好并在后续被当指令执行，就等于永久绕过了确认环节。这类攻击**一次写入、长期生效**，比单轮注入危险得多

**L3 采分点**
- 测试：跨用户读取断言为空；写入恶意指令后断言下一会话不执行；删除后断言检索和衍生索引都查不到

**红旗**：只答「注意隐私」。

## Q36 · 长任务的上下文膨胀怎么处理？ <a id="q36"></a>

**L0 采分点**
- 四种手段：**摘要压缩**（旧历史转摘要）、**结构化状态**（把决策性事实提取成字段而非保留原文）、**外部化 artifact**（大产物存外部，context 里只留引用）、**按需检索**（需要时再取回）
- 核心思路：**从「保留全部历史」转向「保留状态 + 可检索的历史」**

**L1 采分点**
- 摘要的风险是**丢失关键细节且不可逆**。所以正确做法是：原文归档可检索 + 摘要进 context，而不是直接丢弃原文
- 最有效的一招是**结构化状态**：把「用户已确认」「订单号是 X」「资格校验通过」变成任务状态字段。这些字段不会被摘要压缩掉，也不受截断影响（接 [Q30](#q30) 的 L2）
- 分层：近 N 轮保留原文（细节重要）+ 更早的摘要 + 全部可检索
- 成本视角：不压缩的话，多轮 Agent 的 input token 随轮数近似平方增长（接 [Q18](B-推理与服务基础设施.md#q18)）

**L2 采分点**
- 主线项目 M5 的验证目标：跑 20 步任务，**prompt 长度不能无限增长**。第一版没做压缩，第 15 步时 input 已经是第 1 步的 12 倍，成本和延迟都不可接受

**L3 采分点**
- 测试：跑一个 20 步模拟任务，断言 ①每步 input token 有上界 ②压缩后关键决策事实仍在（用一条「第 18 步要用到第 2 步的信息」的 case 验证）

**红旗**：只答「做摘要」，说不出关键事实要结构化保留。
