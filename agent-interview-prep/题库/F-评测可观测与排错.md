# 模块 F：评测、可观测与排错（Q45–Q52）

> **定位**：**资深岗的分水岭**。初级岗几乎不问，高级岗必问且会追到底。

> 这块也是原 48 题版本里质量最高的部分，保留了核心思路，补上了指标定义和排查顺序的细节。

## Q45 · 为什么不能只看最终回答评测 Agent？ <a id="q45"></a>

**L0 采分点**
- 因为**结果可以蒙对**：模型没调工具、调错工具、或者靠参数知识猜，最终文本仍可能正确。而这类通过是不可复现的
- 必须评的四个维度：**最终结果、工具选择与参数、动作顺序（轨迹）、副作用**。外加延迟和成本

**L1 采分点**
- 最典型的漏检是「**回答对、轨迹错**」：模型说「您的订单已取消」但根本没调 `cancel_order`。只看回答会给满分（接 [Q28](C-Agent边界与工具可靠性.md#q28)）
- 反向的「轨迹对、回答错」也存在：工具都调对了，但最终措辞误导用户
- 轨迹评测的粒度要选好：**断言「工具 X 被成功调用」**通常够用；断言「必须按 A→B→C 顺序」太脆，Agent 换个合理顺序就误报
- 副作用维度最容易被忘：评测环境里如果工具是 mock 的，要断言 mock 被以正确参数调用了几次

**L2 采分点**
- 主线项目：加了轨迹断言后，一批原本 92% 通过的用例掉到 71%——差额全是「文本正确但工具未调用或调用失败后模型自行圆场」。这 21% 在线上就是投诉

**L3 采分点**
- 必写的一条 case：**output pass / trajectory fail**。这条是检验评测体系是否有轨迹维度的最快方法
- 通过率要**分维度报告**，不是一个总分：结果通过率、轨迹通过率、副作用正确率。合成一个数会掩盖问题

**红旗**：答「用 LLM judge 打个总分」。

## Q46 · 怎么构建业务 golden set？ <a id="q46"></a>

**L0 采分点**
- 分层构造，**七类都要有**：
  1. 正常路径（happy path）
  2. 边界（临界金额、临界时间）
  3. 缺参数 / 参数模糊
  4. **多个相似候选**（最容易出错，接 [Q25](C-Agent边界与工具可靠性.md#q25)）
  5. 工具失败 / 超时
  6. **应该拒答 / 应该拒绝**
  7. **应该转人工**
- 每条要标：输入、**期望的动作序列**、期望的最终状态、评分方式

**L1 采分点**
- 配比建议：happy path **不超过 40%**。多数人的 golden set 里 80% 是 happy path，导致通过率虚高且对回归无感知
- 第 6、7 类（拒答、转人工）**必须有**，否则在优化过程中模型会变得「更乐于助人」，该拒的不拒——这是最常见的静默回归
- 样本来源优先级：**线上真实失败 > 线上真实成功 > 人工构造**。线上失败样本是最值钱的资产，要建立「失败 → eval case」的固定流程
- 规模：起步 30 条能覆盖分层就有用，不必等 300 条。**分层比数量重要**

**L2 采分点**
- 主线项目 M4：第一版 30 条全是 happy path，通过率 97%，上线后错误率远高于预期。补了缺参、相似候选、工具失败三类共 18 条后，通过率降到 68%——这才是真实水平

**L3 采分点**
- golden set 要**版本化**，每次变更记录原因。否则通过率的变化无法归因（是模型变好了还是题变简单了）
- 定期做**人工抽检**：随机抽 10 条自动判为 pass 的，人工复核，验证评分器没有系统性偏差

**红旗**：答「收集一批真实问题和标准答案」——缺分层，缺期望动作序列。

## Q47 · deterministic eval 与 LLM-as-judge 怎么分工？ <a id="q47"></a>

**L0 采分点**
- **确定性评分**用于：工具是否被调用、参数是否正确、schema 是否合法、权限是否被拦截、关键字段是否匹配、副作用次数
- **LLM judge** 用于：语义正确性、语气、是否回应了问题、是否有幻觉、拒答理由是否合理
- 分界线：**能写出精确断言的一律用确定性**。judge 是没办法时的手段，不是默认手段

**L1 采分点**
- judge 的三个已知问题：**方差**（同样输入不同分）、**位置偏好**（比较时偏向某一侧）、**自我偏好**（偏好同族模型的输出）
- 所以 judge 必须**校准**：用一批人工标注的样本测 judge 与人工的一致率，一致率低于阈值（比如 80%）就不能用
- judge 的 rubric 要**具体可判**：「回答是否有帮助」不可判，「回答中的每个事实断言是否都能在给定证据中找到」可判
- 成本视角：judge 每条 case 都要额外 LLM 调用，全量 judge 在 CI 里跑不起。**确定性做 CI 门禁，judge 做定期抽样**

**L2 采分点**
- 实际现象：同一批 10 题用两种方法评分，分歧集中在「模型给出了合理但不同于期望的解法」——确定性评分判 fail，judge 判 pass。**这类分歧本身是信号**：说明期望答案定得太窄，应该改期望而不是改模型

**L3 采分点**
- 稳定性检验：同一条 case 让 judge 跑 5 次，方差大的 rubric 不可用
- judge 的 prompt 和模型版本要**固定并版本化**，否则评分基线会漂移

**红旗**：全部用 LLM judge，或者认为确定性评测「太死板」。

## Q48 · 通过率 80% 能上线吗？ <a id="q48"></a>

**L0 采分点**
- **单独一个数字无法回答**。要问四件事：
  1. 失败的那 20% 是**什么类型**？（安全类失败 1 条都不能有）
  2. 有没有 **fallback**？（失败能否安全降级到人工）
  3. 这个动作**可逆吗**？（只读 80% 可以，不可逆写不行）
  4. golden set 的**分层构成**是什么？（全 happy path 的 80% 毫无意义）

**L1 采分点**
- 正确的门禁是**分类分档**，不是总分：

| 风险等级 | 例子 | 门禁 |
| --- | --- | --- |
| 只读 | 查订单、答疑 | 总通过率 ≥ 85%，安全类 100% |
| 可逆写 | 建草稿、改偏好 | 总 ≥ 90%，轨迹 ≥ 90%，安全 100% |
| 不可逆写 | 退款、发消息 | 总 ≥ 95%，**必过审批**，安全 100%，且有 kill switch |

- **安全和合规类必须是硬门禁（100%），不能被平均分掩盖**——这是这题的核心采分点
- 平均分掩盖问题的机制：99 条简单题通过 + 1 条越权测试失败 = 99%，但那 1 条是事故

**L2 采分点**
- 上线决策还要看**失败的代价分布**：错误退款 ¥10 和 ¥10000 不是一回事。所以要按金额分段看通过率

**红旗**：直接回答「能」或「不能」。

## Q49 · 如何定位一次失败：eval 问题、Agent 问题，还是平台问题？ <a id="q49"></a>

**L0 采分点**
- 固定排查顺序，**从外向内，不能跳步**：
  ```
  0. 基础设施健康吗？  API 可用、索引在线、凭据有效、限流、版本
  1. eval 本身有效吗？ 期望答案还对吗、评分器稳定吗、测试环境正常吗
  2. 轨迹在哪步偏离？  检索 → 路由 → 工具 → 状态 → 审批
  3. 归因：Agent 配置可修 / 工具数据可修 / 平台限制
  4. 修复后重跑同一 case + 相邻负向 case
  ```
- **第 4 步是最常被跳过的**：只重跑失败的那条，会造成局部优化导致别处回归

**L1 采分点**
- 为什么先查 eval 而不是先改 Agent：**改 prompt 是最容易做、最容易产生假象的动作**。期望答案过期、评分器抖动、mock 数据变了，都会表现为「Agent 变差了」
- 「幽灵问题」的定义：花时间修了一个其实不存在的问题，因为根因在评测侧。这是这套顺序要防的主要风险
- 平台限制的识别：同样的输入在 playground 里也复现 → 不是你的配置问题

**L2 采分点**
- 实际案例形态：一批 case 突然全红，第一反应是模型更新了。按顺序查发现是**测试用的 mock 订单数据过期**（订单状态被定时任务改了），eval 侧问题。如果当时直接去改 prompt，会白改两天并且引入真实的回归

**L3 采分点**
- 每次失败要记录：**假设 → 排查路径 → 真因 → 修复 → 回归验证**。这个记录就是面试时「讲一个你 debug 的例子」的素材（见 [故障注入/清单.md](../故障注入/清单.md)）

**红旗**：第一反应是改 prompt。

## Q50 · Trace 至少要记录什么？ <a id="q50"></a>

**L0 采分点**
- 十类字段：
  ```
  标识    trace_id / task_id / tenant_id / user_id(脱敏)
  版本    prompt 版本 / 模型 + 版本 / 工具 schema 版本 / 代码版本
  输入    用户输入(脱敏) / 系统指令引用(不存全文，存版本号)
  检索    query / 命中文档 id + 分数 / 是否 rerank
  工具    名称 / 入参(脱敏) / 出参(脱敏) / 耗时 / 成功失败 / 重试次数
  状态    状态转移序列
  预算    每步 token / 累计 token / 缓存命中 / 成本
  时间    每步耗时 / 端到端
  错误    错误码 / 是否可重试 / 最终终止原因
  人工    审批请求 / 审批人 / 结果 / 耗时
  ```

**L1 采分点**
- **版本字段是最常被漏的**，也是排错时最有用的——没有它你无法回答「上周好好的，改了什么？」
- **脱敏要在写入前做**，不是查询时做。trace 会被广泛访问，是数据泄露的高风险面
- trace 的结构应该是 **span tree**（一次任务是根，每轮/每工具是子 span），不是扁平日志。扁平日志无法看出因果和耗时归属
- 采样策略：全量存成本高。做法是**失败和慢请求 100% 采样，成功请求按比例采样**

**L2 采分点**
- 主线项目 M0 就补了 trace，因为没有 trace 时一个「取消失败」查了两小时；有了之后同类问题 5 分钟定位（这条数字对比很有说服力）

**L3 采分点**
- 自查方法：拿一条线上失败，只看 trace 能不能还原出「发生了什么、为什么、该改哪」。不能就说明字段不够

**红旗**：只答「记录输入输出」。

## Q51 · 回归与灰度怎么做？ <a id="q51"></a>

**L0 采分点**
- 四件事：**版本化数据集** → **CI 门禁**（安全类必过、总通过率不低于基线）→ **shadow / canary**（影子跑或小比例）→ **可回滚 + kill switch**
- 加一条闭环：**线上失败自动转成 eval case**，否则同样的问题会反复出现

**L1 采分点**
- prompt 改动**必须走和代码一样的流程**：版本化、code review、CI 跑 eval、灰度。把 prompt 当配置随手改是事故高发区
- **shadow 模式**（线上流量复制一份给新版本跑，结果不返回用户）对 Agent 特别有价值——可以在零风险下拿到真实流量的对比数据。但有副作用的工具在 shadow 下必须 mock
- 灰度比例要按**风险**定，不是按流量定：不可逆写操作从 1% 起，只读可以直接 10%
- 回滚要能**在分钟级完成**，且要考虑**状态兼容**——灰度期间产生的任务状态，回滚后旧版本能不能读

**L2 采分点**
- 容易踩的：只跑改动相关的 case 就上线，结果影响了别的路径。所以 CI 门禁必须跑**全量 golden set**，不能只跑相关子集

**L3 采分点**
- 灰度期间要对比的指标：task success、轨迹通过率、p95、cost per successful task、转人工率、**用户重试率**（最敏感的体验信号）

**红旗**：答「上线前测一下」。

## Q52 · 线上指标怎么避免被平均值误导？ <a id="q52"></a>

**L0 采分点**
- 三条原则：**分段**（按任务类型/风险等级/工具/租户/渠道）、**看分位数**（p50/p95/p99 而非均值）、**按失败原因拆分**（不是一个 error rate）
- 核心指标应该是 **cost per successful task** 和 **task success rate**，不是 cost per call 和 error rate——后者会奖励「早早失败」

**L1 采分点**
- 八个该上 dashboard 的分段指标：
  1. task success rate（按任务类型分段）
  2. 轨迹通过率（工具是否按预期调用）
  3. p95 端到端延迟（按任务类型分段）
  4. cost per successful task
  5. 转人工率 + 转人工原因分布
  6. 失败原因分布（参数不足/无权限/工具失败/业务拒绝/超预算）
  7. 平均轮数 + 轮数 p95（成本和体验的先行指标）
  8. **用户重试率 / 重新表述率**（最敏感的质量信号，先于投诉出现）
- 平均值的具体骗法：大量简单只读任务拉低平均延迟和成本，掩盖了复杂写任务的糟糕表现

**L2 采分点**
- 实际现象：总体成功率 94% 看起来很好，按任务类型拆开后「退款」这一类只有 71%——而它恰恰是最高风险的那类。分段之前完全看不见

**L3 采分点**
- 告警要基于**分段指标 + 环比**，不是绝对阈值。绝对阈值在流量结构变化时会大量误报

**红旗**：只报一个总体准确率。
